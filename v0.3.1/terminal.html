Middleware: the terminal contract

Version 5, 13-Nov-2026. This count numbers the frames of this page alone. It ends at 5. From now on, the frames change with a release of the middleware, and that release is not this count. Read the release in serverInfo.version from the sandbox’s MCP server, or in SandboxVersion in a conformance report. The release of the middleware a terminal connects to is in that host’s own GET /v1/health, in Version.

Version 5 adds the refund. An Instruction may now carry TransactionType RFND and an OriginalTransaction, the sale to refund: refund TotalAmount against that sale, and report it in an Outcome as a sale’s (A refund, below). The middleware sends a refund only to a terminal that says on its upgrade that it takes refunds, in the header Mw-Transaction-Types: CRDP, RFND (Connect, below). A terminal built to version 4 sends no such header, so it is never sent a refund: it would ignore the two keys it does not read and charge the refund as a sale. Declare RFND only once the terminal reads TransactionType.

Version 4 makes the word a terminal shows while a register links a pair: LinkWord’s Word holds two different words of the middleware’s list, in order, joined by a dot, such as rabbit.lamp. A terminal built to version 3 that shows Word as it comes shows the pair; one that checks the frame against version 3’s pattern refuses it, so build it to this version (Linking to a register, below).

Version 3 states the outcome in ISO 20022’s payment terms: a TransactionStatus of ACSP or RJCT, a StatusReasonInformation whose Reason says why no payment was taken, and the references grouped by the kind of payment, Card, Bank, Wallet and NPP. An outcome built to version 2 holds no TransactionStatus, so the middleware refuses it as missing_field: build the outcome to this version (Outcome, below).

Version 2 adds the client certificate a live terminal presents, and the two frames a terminal is sent while a register links to it, LinkWord and LinkEnded. A terminal built to version 1 ignores both frames, as it ignores any frame it does not know, and shows no word.

This is the contract a payment terminal implements to take payments through the middleware. The middleware relays a sale, or a refund of one, from a point of sale (POS) to a terminal, and the terminal’s outcome back to the POS. A terminal that needs a session at its fleet’s own payment system can ask the middleware for what that system takes to sign it in, and report what that system answered in a LoginResponse (Signing in, below). You can build a terminal’s side from this document alone. The schema of each frame, TerminalInstruction, TerminalOutcome, TerminalRefusal, TerminalLinkWord, TerminalLinkEnded, TerminalStatusRequest, TerminalAbort, TerminalLoginNeeded, TerminalLoginRequest and TerminalLoginResponse, is also in docs/api/openapi.yaml beside it, for a client that validates what it sends and receives.

An instruction is a sale, or with TransactionType RFND a refund, and only a terminal that declared RFND is sent a refund. Field names are ISO 20022 element names as written, in PascalCase. Every field below says who sends it: mw or terminal. Every amount is a JSON string in decimal major units with a dot and exactly two fraction digits, such as "12.50". It is never a JSON number and never negative, and one Currency, AUD, governs every amount in a sale.

In short

  1. Open a WebSocket to /v1/terminals/{POIIdentification}/connect, presenting the terminal’s credential on the upgrade, and hold it while the terminal is on. Reconnect whenever it closes.
  2. If the terminal takes refunds, say so on every upgrade, beside the credential: Mw-Transaction-Types: CRDP, RFND. A terminal that says nothing is sent sales alone. Once it answers a StatusRequest, say that too: Mw-Message-Functions: SSMQ. Once it also answers an Abort, add SSAB: Mw-Message-Functions: SSAB, SSMQ. Once it does all that Signing in, below, says, add SASQ: Mw-Message-Functions: SASQ, SSAB, SSMQ.
  3. An Instruction frame arrives. Store its TransactionReference, then charge TotalAmount, or with TransactionType RFND refund it (A refund, below).
  4. When the payment ends, store the Outcome frame, then send it.
  5. If the middleware answers with a Refusal, read its code. Otherwise the outcome counts as taken once any later frame but a Close comes from the middleware on that connection. Taken or not, send your most recent outcome again after any reconnect, until a new Instruction, a Refusal for it other than terminal_not_permitted, or 23 hours.
  6. If a LinkWord frame arrives, show its word until a LinkEnded comes or its seconds pass (Linking to a register, below).
  7. If a StatusRequest frame arrives, answer it from what the terminal stored (StatusRequest, below).
  8. If an Abort frame arrives, stop the payment its TransactionReference names if it has not reached the host, and send RJCT with DS02. Otherwise answer it from what the terminal holds (Abort, below).
  9. If the terminal declared SASQ and holds no session at its fleet’s payment system, at connect or when an Instruction arrives, wake if it sleeps, send one LoginNeeded with a fresh key, open the LoginRequest that answers it, sign in with what it holds, and report what its fleet’s payment system answered in one LoginResponse (Signing in, below).

The sections below say what each step means, and what to do when a step goes wrong.

Address

A terminal is tested in the middleware’s sandbox, which serves this document. The sandbox’s start page, mw://start through its MCP server and /docs/api/sandbox.md over HTTP, walks a terminal from a first key to a signed conformance report. POST /sandbox/v1/keys needs no credential, and answers a sandbox key and a world of nine terminals, one of them <tester>-yours, which nothing in the sandbox holds and your terminal connects as.

A terminal connects to the address the sandbox served this document from, its scheme made WebSocket’s: ws:// where that address is http://, and wss:// where it is https://, on the same host and port. The path is /v1/terminals/{POIIdentification}/connect, with the terminal’s own id in it (The id, below), and its credential goes on the upgrade (Connect, below). Two connections for one id replace each other, because each reconnects when it is closed, so connect each terminal under its own id.

A live middleware is wss:// on port 443. /docs/api/environments.md names the base URL of each environment open to an integration.

The id

POIIdentification is the terminal’s id, and matches ^[A-Za-z0-9_-]{1,64}$. The middleware issues it, poi_ then 32 lowercase hex characters, when the terminal’s fleet lists the device, and the POS names the same id in its sale. Only a seed, which a sandbox reads at boot, may choose one instead. A listed terminal may connect once it is paired: in the sandbox, a seed pairs it. It must not be a card or account number: the middleware cannot detect one in it, and the id is logged.

Connect

GET /v1/terminals/{POIIdentification}/connect with a WebSocket upgrade (RFC 6455): Connection: Upgrade, Upgrade: websocket, Sec-WebSocket-Version: 13 and a Sec-WebSocket-Key. Every message either way is a text frame holding one JSON object in UTF-8, at most 65,536 bytes. The only other frames are WebSocket’s own Ping, Pong and Close.

The credential. A live terminal presents its client certificate at the TLS handshake of the upgrade, with the issuing certificate beside it, as CertificateChain gave them, and sends no Authorization header. The middleware’s own CA issues it when the terminal enrols: POST /v1/enrol with the PairingCode its listing showed, a CSR for a P-256 key the terminal made in its keystore, its SerialNumber, and its Android Key Attestation chain. A terminal’s code is five words of docs/api/words.txt, such as bronze.farm.loop.prism.tempo, and docs/api/onboarding-device.md walks how an app reads them. The certificate names the terminal’s POIIdentification, which must be paired, and lasts 30 days. Once a day, GET /v1/certificates/self under it answers RenewNow. When that is true, ask POST /v1/certificates/challenge, make a new key with that challenge, renew with POST /v1/certificates/renew, use the new certificate from the next connection, and delete the old key once a connection on the new one has succeeded. docs/api/openapi.yaml holds each of these routes.

A sandbox terminal may present its sandbox key on the upgrade instead, as Authorization: Bearer sbx_...: a pos key of the terminal’s own vendor, on a POIIdentification that is paired for that vendor. A pos key names a register of its own vendor, and only a vendor holding pos may list one, so in a sandbox the terminal’s fleet vendor must also hold the pos role and a register, whose pos key the terminal presents. FUNDiMO issues the key, and it is shown once. A live middleware refuses every sandbox key. One credential a request: a certificate and an Authorization header together are refused. The middleware checks the credential first, then the id, then the upgrade. No frame changes for it.

What the terminal takes. A terminal that takes refunds says so on the upgrade, beside its credential, in the header Mw-Transaction-Types: ISO 20022 codes of TransactionType, separated by commas with optional spaces, such as Mw-Transaction-Types: CRDP, RFND. CRDP is a sale and RFND a refund. The middleware sends a refund only on a connection whose upgrade declared RFND: a POS that asks for a refund on a terminal connected without it is refused 409 terminal_cannot_refund, and the terminal is sent nothing. Absent, empty, over 256 bytes, or naming no code the middleware knows, the header reads as CRDP alone. A code it does not know is ignored, codes are matched exactly, case and all, and CRDP is always in the set, so a terminal that declares RFND alone is still sent sales. Sent more than once, its values are read as one list. The middleware keeps what a connection declared for that connection alone, and a new one carries its own, so send the header on every upgrade. It reads the header only once the credential has passed, and a refused upgrade reads it not at all. ISO 20022 has no element for it: the name is the middleware’s own.

What the terminal answers, and what it asks. A terminal says on the upgrade which of the middleware’s requests it answers, and whether it asks to be signed in, in the header Mw-Message-Functions, read as Mw-Transaction-Types is: codes separated by commas with optional spaces, read as one list when the header is sent more than once, matched exactly, case and all, a code the middleware does not know ignored, and kept for that connection alone, so send it on every upgrade. Its codes are ISO 20022’s MessageFunction, of Header41: “Identifies the type of process related to the message.” SSMQ, “Request the status of a previous message for which the Sale system has no response.”, says the terminal answers a StatusRequest (StatusRequest, below), such as Mw-Message-Functions: SSMQ. SSAB, “Abort the current process or the last request.”, says the terminal answers an Abort (Abort, below), such as Mw-Message-Functions: SSAB, SSMQ for a terminal that answers both. SASQ, “Request the management of a session: login, logout and diagnosis services. Initiated by the Sale system.”, says the terminal asks to be signed in to its fleet’s payment system, and can be woken (Signing in, below), such as Mw-Message-Functions: SASQ, SSAB, SSMQ for a terminal that does all three. The middleware sends an Abort only on a connection whose upgrade declared SSAB: a POS that asks to cancel a sale on a terminal connected without it is refused 409 terminal_cannot_abort, and the terminal is sent nothing. The middleware answers a LoginNeeded only on a connection whose upgrade declared SASQ: on any other it is refused unknown_frame_type. Absent, empty, over 256 bytes, or naming no code the middleware knows, the header declares none, the terminal is sent no StatusRequest and no Abort, and its LoginNeeded is refused. Declare SSMQ only once the terminal answers a StatusRequest, SSAB only once it answers an Abort, and SASQ only once it does all that Signing in, below, says. The middleware reads the header only once the credential has passed, and a refused upgrade reads it not at all. ISO 20022 has no element for the header itself: its name is the middleware’s own.

A non-2xx answer from the middleware has the body { "Error": { "Code": "...", "Message": "...", "Fields": [] } }.

Hold

Keep the connection open while the terminal is on. The middleware sends a WebSocket Ping every MW_WS_PING_SECS, 30 seconds by default. Answer each with a Pong, which most WebSocket libraries do by themselves. The middleware treats 2.5 intervals with no frame of any kind from the terminal as a dead connection, and closes it. Treat the same silence the same way: assume the default, and close and reconnect after 75 seconds with no frame from the middleware.

A WebSocket library may answer each Ping itself and never show it, as OkHttp does. On one, the middleware’s Pings cannot be counted, so send your own: set the library’s ping, pingInterval(30, TimeUnit.SECONDS) on OkHttp’s client, and read the library failing the socket for want of a Pong as that silence, and reconnect. The middleware answers each Ping with a Pong, and counts it as a frame from the terminal. Since such a library shows none of the middleware’s Pings, the later frame of Resending is safe, below, is the next text frame from the middleware: an Instruction, a StatusRequest, an Abort, a LinkWord, a LinkEnded or a LoginRequest. An Instruction that comes is the next payment as well.

Reconnect

After any close, and after a failed connect the table above does not say to fix, reconnect with a backoff: wait 1 second, double the wait after each failure up to 30 seconds, and add a little randomness. A connection that closes within 10 seconds of opening counts as a failed connect, so the next wait still doubles. Reset the backoff to 1 second only once a connection has stayed open 10 seconds. This keeps a store outage, where the middleware closes the connection on each outcome it cannot record, from becoming a reconnect every second. After a refusal on connect, the holder’s table says how long to wait (What a holder of a dead certificate does, above).

A new connection for the same id takes over from the old one, and the middleware closes the old one itself: it sends what was already queued for it, then a WebSocket Close, or drops it if it takes no writes. A frame already queued for the old connection goes out on it or not at all, never on the new one, so open a second connection only to replace the first.

The middleware keeps reading the old connection until the terminal closes its side, for at most 2.5 times MW_WS_PING_SECS after the takeover, 75 seconds by default. An outcome read there is logged and applied as on any connection, so an outcome sent on the old connection as the new one opened still settles its sale. Three things differ there:

  • A Refusal can be lost. The middleware stops queueing frames for the old connection as the new one opens, and a Refusal it cannot queue gets a delivery_failed line in its log and is never sent.
  • A frame that ends the old connection, a frame or message over 65,536 bytes or a frame that breaks the WebSocket protocol, leaves no line of its own: the connection’s one terminal_disconnected line gives the reason replaced, not that frame’s.
  • A frame still unread when that time is up is never read, and leaves no line.

So send nothing more on a connection once a new one is open, and send your most recent outcome again on the new one, as Resending is safe, below, says.

A drop does not end a sale. An outcome that could not be sent before a drop is sent after the reconnect. A hosted middleware will close connections of its own accord, so the reconnect is not optional.

The middleware also closes the connection when its store cannot take an outcome the terminal sent, because the store is down or slow. Its log’s terminal_disconnected line then gives the reason store_unavailable, and the outcome may not have been recorded. Send it again after the reconnect, as Resending is safe, below, says.

The middleware closes a connection whose terminal stops being paired, or whose credential is retired, within MW_WS_PING_SECS, and its log’s terminal_disconnected line gives the reason revoked. While that lasts, the next connect is refused: 403 not_permitted backs off to one hour, and a retired credential’s refusal is read by the holder’s table above. Keep any outcome you hold.

A hosted middleware may run two instances for a while, and a POS’s sale can reach the one your connection is not on. That instance answers the POS 409 terminal_offline, and the one your connection is on closes it within a few seconds; its log’s terminal_disconnected line gives the reason moved. Reconnect as after any close: your next connection reaches the instance taking new requests.

Linking to a register

A register links to a terminal at the counter, by a word the terminal shows. The register asks the middleware, the middleware gives each unbound paired terminal of the store a different word, and the staff member types the word they see on the terminal in their hand into the register. The word is a pair: two different words of the middleware’s list, in order, joined by a dot, such as rabbit.lamp, and the staff member types the two with the dot or a space between them. The POS never sees a word: the word is the whole proof that the person at the register holds that terminal. Two frames reach the terminal, and neither needs anything back.

What to charge. The terminal charges TotalAmount and shows it as the total, whatever the items say, and takes the payment whether or not it can show the items. It adds nothing to TotalAmount: no surcharge, tip or fee, neither its own nor one its merchant settings would apply to a payment it starts itself, so switch those settings off for a payment the middleware instructs. A store’s own surcharge on the bill, such as 15% on a public holiday, is already inside TotalAmount: the POS added it before it sent the sale, so never add it again. No card payment surcharge is taken through the middleware. A refund refunds exactly TotalAmount (A refund, below). The approval states what the host approved, in TransactionDetails.AuthorisedAmount (Outcome, below), and the middleware logs one other than TotalAmount as the terminal breaking this contract.

The items. Show the items if the terminal can, and ignore SaleItem if it cannot. They never change what is charged, and a terminal never adds them up. Assume no length or alphabet for ProductDescription, and clip what cannot be shown: the schema gives that field no pattern, so the bound can widen later. The POS’s ProductCode, tax, discounts, product identifiers and the basket’s header stay in the middleware.

What a terminal ignores. Ignore any key a frame the middleware sends does not name, at any depth, on an Instruction, a Refusal, a LinkWord, a LinkEnded, a StatusRequest, an Abort and a LoginRequest, and in the SignedValue group a LoginRequest opens to: a later version may add some. Ignore a frame of any MessageType the terminal does not know.

The middleware sends each instruction once. A drop does not bring it back. Instead, the middleware asks about an instruction lost in a drop on a later connection of the terminal, by a StatusRequest, when that connection declared SSMQ (StatusRequest, below). If a TransactionReference the terminal has already started arrives again, do not charge again: resend its stored outcome if it has one. An instruction the terminal cannot act on, such as a Currency it does not support, gets RJCT with Reason AB11, because no payment was taken.

Keep the reference first. Store the TransactionReference before taking the card, so a crash or a reboot can still report. On restart, find out from the host what happened, then send the outcome.

A refund

An Instruction with TransactionType RFND is a refund: a sale running the other way, sent and settled as a sale is. The POS asks for it against a sale the middleware approved, and the middleware adds what it kept of that sale, under OriginalTransaction:

{ "MessageType": "Instruction", "TransactionType": "RFND", "TransactionReference": "sal_02a8f3c4d5e6f708192a3b4c5d6e7f80", "SaleReferenceIdentification": "CN-1001", "TransactionDetails": { "Currency": "AUD", "TotalAmount": "6.25", "SaleItem": [ { "ProductDescription": "Flat white", "ProductQuantity": 1, "UnitPrice": "6.25", "ProductAmount": "6.25" } ] }, "OriginalTransaction": { "TransactionReference": "sal_01970f6e7c3a7d3e8a4f2b1c9d0e1f2a", "POIIdentification": "T-APPROVE", "SaleReferenceIdentification": "INV-1001", "TransactionDateTime": "2026-11-06T15:12:40+11:00", "PaymentReference": { "Card": { "RetrievalReferenceNumber": "631012345678", "SystemTraceAuditNumber": "000123", "AuthorisationCode": "A1B2C3", "AcquirerPOIIdentification": "12345678", "RefundReference": "klujhadsc9ph87asd" } } } }

TransactionType is ISO 20022’s TransactionType (TxTp) of PaymentTransaction183: “Type of transaction being undertaken for the main service.” Its codes are ISO’s CardPaymentServiceType16Code: CRDP, “Card payment.”, and RFND, “Refund transaction.” ISO names them for cards, and this contract uses them for every rail. OriginalTransaction is ISO’s OriginalTransaction (OrgnlTx): “Identification of the original transaction.” Each definition is ISO’s, from M3 (Sources, below).

Declare it first. The middleware sends a refund only on a connection whose upgrade said the terminal takes refunds, Mw-Transaction-Types: CRDP, RFND (Connect, above). A terminal that declares nothing is sent sales alone, so one built to an earlier version, which would ignore TransactionType and charge the amount, is never sent a refund.

Read TransactionType first. With RFND, store the TransactionReference, which is the refund’s own, then refund TotalAmount, the amount to refund, against the sale OriginalTransaction names. Refund by its references where the host can retrieve the original transaction, and with the card presented where it cannot, never replaying the sale’s authentication data. A payment over NPP, PayTo included, or through a wallet or payment app, is refunded through the app or provider that took it, by the ids of its group in OriginalTransaction.PaymentReference. The refund’s terminal need not be the sale’s: OriginalTransaction.POIIdentification names the one that took it, and a host whose references do not reach across its own terminals declines. A code the terminal does not take, or a refund it cannot make for this kind of payment, gets RJCT with Reason AB11, and moves no money.

The outcome is a sale’s. Report the refund in an Outcome under the refund’s own TransactionReference, never the sale’s: ACSP when the whole TotalAmount was refunded, RJCT with AG07 when the host declined the refund, RJCT with DS02 when the terminal stopped the refund, before it reached the host, in answer to an Abort (Abort, below), and RJCT with AB11 for every other way no refund was made (Which TransactionStatus to send, below). The refund’s own references, such as the host’s new retrieval reference, go under the groups and keys of References by kind, below. Store the outcome, send it, and send it again after any reconnect, as a sale’s (Resending is safe, below). A TransactionReference the terminal already started is never refunded twice.

No total is kept. The middleware keeps no total of a sale’s refunds: it relays every refund, whole or part, however many the sale has had, and does not compare a refund’s amount with the sale’s. A host that caps a sale’s refunds declines the one past its cap, and the terminal sends RJCT with AG07.

A refund’s UNKN is a sale’s. A refund has a sale’s deadline and hold: with no outcome by MW_SALE_DEADLINE_SECS, the POS reads UNKN, and a late outcome replaces it unless the terminal contradicted itself. The middleware sends a refund’s instruction once and holds no amount for it. A refund the terminal never received is asked about on a later connection, by a StatusRequest, as a sale’s is (StatusRequest, below). Until the terminal answers, the POS reads UNKN, and the cashier checks the terminal before refunding another way. Always send a refund’s outcome, however late.

One payment at a time

The middleware sends no second instruction while a sale or a refund holds the terminal. If one arrives anyway, do not start it and do not queue it: store RJCT with AB11 as the outcome of its TransactionReference, and send it. No payment was taken for it, and the POS reads that as a definite answer. Queueing is how a customer pays twice. A terminal with a payment it cannot yet resolve is still busy, even after the middleware’s hold ends, so the same applies.

Deadline

Send the outcome as soon as it is known. If the middleware has heard nothing by MW_SALE_DEADLINE_SECS, 120 seconds by default, it tells the POS UNKN. The terminal stays claimed for MW_TERMINAL_HOLD_SECS more, 180 seconds by default, so no new sale reaches it while it may still be mid-payment.

Always send the outcome, however late. A late outcome replaces UNKN, and is the only way the POS learns the truth.

The middleware holds a sale for MW_SALE_RETENTION_SECS, 86,400 seconds by default, which is 24 hours, after it settled or went UNKN. After that, an outcome for it gets not_held.

Signing in

A terminal may need a session at its fleet’s own payment system before it can take a payment, and may hold none: after its process starts, or once that system ended the session. A terminal that declared SASQ (Connect, above) asks the middleware for what that system takes for a sign-in, with a LoginNeeded. The middleware answers on the same connection with a LoginRequest, made from the credential the fleet set for the terminal’s store and sealed to a key the terminal made for that one asking, or with a Refusal saying why not. The terminal opens the answer, takes it to its fleet’s payment system itself, and reports what that system answered in a LoginResponse. The middleware never sees the session and cannot end it: ending one is the fleet’s. A POS changes nothing for it: it sends no new field and reads no new code, and a sale to a terminal that signs in reads as any sale.

SASQ is ISO 20022’s RetailerMessage1Code SASQ: “Request the management of a session: login, logout and diagnosis services. Initiated by the Sale system.” ISO 20022 has no message by which a terminal asks for a login: LoginNeeded is the middleware’s own name. LoginRequest is named after ISO 20022’s LoginRequest, of SessionManagementRequest9, “Content of the Login Request message.”, and carries none of its elements. LoginResponse is named after ISO 20022’s LoginResponse, the block a POI sends to answer a login, of SessionManagementResponse9, “Content of the Login Response message.”, and carries none of its elements either. Each definition is ISO’s, from M3 (Sources, below).

When to ask

Declare it. Send SASQ in Mw-Message-Functions on every upgrade, once the terminal does all this section says. Declaring SASQ declares that the terminal can be woken.

Wake. Given an Instruction while it is asleep, its screen off or its application not in front, a terminal that declared SASQ turns the screen on and brings its payment screen to the front over the lock screen, then asks if it holds no session. The middleware cannot see the screen, and neither can a conformance run, so this is the contract’s rule alone.

Ask. A terminal asks only while it holds no session at its fleet’s payment system: on an Instruction, or at connect where it knows it holds none, which takes the round trip off the sale’s path. It asks at most once a connection, unless its fleet’s payment system refused what it was sent. For each asking it makes a fresh P-256 key pair in memory, not in its keystore, and sends one LoginNeeded holding the public key, then reads the answer before its next frame, as Refusal, below, asks of every frame.

No credential at the store. The ask is refused sign_in_not_available, and a terminal signed out is normal: answer the sale RJCT with AB11, unless a person signs in at the terminal by its fleet’s own means, and ask no more on that connection.

A credential attached. The terminal is woken, signs in with what it is sent, reports what its fleet’s payment system answered, and takes the sale.

Resending is safe

Resending is safe, and the only safe change is none. The middleware does not acknowledge an outcome, so a terminal cannot be sure one arrived.

  • Store the frame before sending it.
  • Treat an outcome as taken once any later frame but a Close has come from the middleware on the same connection, such as a Ping or an Instruction, with no Refusal for it. On a library that never shows a Ping, it is the next text frame (Hold, above). That frame shows the connection was still alive after the outcome went. A Refusal that comes later is still about it while it is the last frame sent (Refusal, below). This decides when the terminal goes on to its next payment, and does not end the resend below.
  • After any reconnect, send your most recent outcome again, unchanged, whether or not you think it arrived, and judge it there the same way. That covers a drop, a restart of the terminal, a close after 75 seconds of silence (Hold, above), a newer connection replacing this one, where the middleware sends what was queued for it and then a Close, and a Refusal on it can be lost (Reconnect, above), and the middleware closing the connection because its store could not take the outcome.
  • Stop sending it again when a new Instruction arrives, when the middleware answers it with any Refusal but terminal_not_permitted, or 23 hours after you first sent it. After a Refusal, do not resend that frame (Refusal, below), with one exception: after terminal_not_permitted, keep the outcome, close the connection, reconnect, and send it again. 23 hours stays inside the middleware’s default retention of 24 hours (Deadline, above), so a terminal left idle does not end on a not_held an operator would have to read.
  • This resend is the only recovery for an outcome the middleware closed the connection on and could not record, because the middleware sends no acknowledgement. It replaces any judgement of how soon a close must follow a send: the middleware may take several seconds to close when its store is slow.
  • A repeat of what the middleware holds changes no sale and gets no reply, so sending again after a reconnect is always safe. On one connection, send a sale’s outcome at most once, and never again on a timer: each repeat is another line in the middleware’s log. The sandbox’s conformance run fails a terminal it sees repeating an outcome on one connection, and a green run does not prove a terminal never does.
  • A different TransactionStatus or Reason, or a different value under one path of PaymentReference, its group and key, is a contradiction: the sale reads UNKN for good. An outcome that only adds a key is a repeat, and so is one whose ResponseCode, AdditionalInformation or TransactionDetails.AuthorisedAmount alone differs: the amount first applied stands. A key of the same name in two groups is two keys.
  • The middleware queues a refused frame’s Refusal on the frame’s own connection as soon as it has read and judged the frame. On a connection that stays open, it is lost only where the middleware cannot queue it: on a connection a newer one has replaced, and on one where 8 frames already wait because the terminal is not reading them. A connection that ends, by a drop, a write that fails, the end of a takeover’s drain, the middleware closing it on a store failure, or the middleware stopping, can take a queued Refusal with it. The connection closing is the sign: send the outcome again after the reconnect, as above.

The reference text rule. Six keys hold free text whose issuer sets its format: Card.RefundReference, Bank.AccountServicerReference, Wallet.RecipientTransactionIdentification, and the three NPP keys. A value that fails is dropped alone

A value that fails its pattern is dropped alone, and the outcome still applies. The middleware’s log names it in a fields_dropped line by its full path, as TransactionDateTime or PaymentReference.Card.RetrievalReferenceNumber, and its value is written nowhere. The POS gets the rest, and does not get that value.

  • A key sent as null, an empty object, and an object emptied by drops read as absent.
  • A StatusReasonInformation, a PaymentReference or a group that is not an object is dropped whole. A ResponseCode or AdditionalInformation that is not a string is dropped alone.
  • A Reason sent with ACSP is dropped alone and named in fields_dropped: it decides nothing there, so it never refuses the outcome.
  • TransactionStatus is different, because the outcome cannot stand without it: absent is missing_field, and anything else wrong is invalid_result. So is Reason with RJCT: absent, or in a StatusReasonInformation that is not an object, is missing_field, and anything but AG07, AB11 or DS02 is invalid_result.
  • A key in another case, such as RRN or responsecode, is an unknown field, and dropped. So is a group or a key that References by kind does not list, such as a card key sent at PaymentReference’s top level, by its path, its value unread.
  • The middleware does not trim, so a padded AuthorisationCode such as "AB12 " is dropped. Strip padding, and zero fill SystemTraceAuditNumber.
  • If a key is repeated in a frame, the last value wins, and it is held to the same rules.
  • Three things are never dropped alone, because the middleware cannot parse a frame that holds one, in any field: a \u escape of half a surrogate pair with no other half, such as \ud83d alone; a number beyond the range of an IEEE 754 double, such as 1e400; and arrays and objects nested 128 deep, the frame’s own object counting as one. A frame holding one is refused whole as unparseable_frame, and its outcome does not apply. Never send them: cut a string between whole characters, never inside a surrogate pair.

The middleware reads a connection’s frames in the order they were sent, queues a refused frame’s Refusal as soon as it has read and judged the frame, and sends what it queued for a connection in that order. So send one frame at a time, and read any Refusal for it before sending the next.

A Refusal the middleware cannot queue is lost, and the middleware’s log holds a delivery_failed line for it: on a connection a newer one has replaced (Reconnect, above), and on one where 8 frames already wait because the terminal is not reading them. A frame the middleware reads but does not apply gets no Refusal and no delivery_failed line, though its in line is logged: one read while 8 frames before it still wait to be applied, which closes the connection, and one still waiting when the connection closes.

A refused frame changes nothing, so the sale waits for a good one, and the terminal goes on to its next payment. Apart from not_held, terminal_not_permitted, sign_in_not_available, sign_in_limited and sign_in_unavailable, a Refusal means a bug in the terminal’s code, which a running app cannot fix, so do not resend that frame. Keep an outcome it refused, so the outcome can be sent once the code is fixed. A refused LoginNeeded is never kept or resent: its fresh key is dropped (Signing in). Nor is a refused LoginResponse: the terminal goes on as Signing in, above, says. terminal_not_permitted is the one exception to do not resend: it is no bug, so keep the outcome, close the connection, reconnect, and send it again. A suspension that lifts then loses nothing.

An outcome that was taken gets no reply: there is no acknowledgement. Nor does a LoginResponse that was taken. A frame or message over 65,536 bytes closes the connection instead of getting a Refusal, and so does a frame that breaks the WebSocket protocol, such as invalid UTF-8 in a text frame. Either way the frame is lost, so resend its outcome after the reconnect.

The paths, step by step

The normal path.

  1. Connect, and hold the connection.
  2. An Instruction arrives. Store its TransactionReference, then show TotalAmount as the total, and the items if the terminal can.
  3. Take the payment for TotalAmount, or with TransactionType RFND make the refund of it (A refund, above).
  4. Build the Outcome with the instruction’s TransactionReference, and the TransactionStatus, with its Reason on RJCT, that Which TransactionStatus to send, above, gives. Store it, then send it.
  5. No Refusal arrives, and a later frame from the middleware does, such as its next Ping, or on a library that never shows one its next text frame (Hold, above): the outcome was taken, and the terminal is free for its next payment. Taken or not, it is still the most recent outcome, so after any reconnect take the resend path below.

The resend path. The connection drops or the middleware closes it, or the terminal restarts, after the terminal sent an outcome, and before a new Instruction, a Refusal for it other than terminal_not_permitted, or 23 hours after it was first sent.

  1. Reconnect with the backoff.
  2. Send the stored frame again, unchanged.
  3. The middleware applies it if it had not arrived, and ignores it if it had. Either way no reply comes, and the sale reads the result that frame carries. The one exception is a sale the middleware no longer holds, past retention: that outcome gets not_held, below.
  4. Do the same after every later reconnect, until one of those three ends.

If the same TransactionReference arrives again in an Instruction, do not charge again: send the stored outcome.

The unknown-result path. The terminal does not know whether a payment was taken, for example because the host did not answer.

  1. Send nothing for that sale yet. The terminal is still busy: start no other payment.
  2. Ask the host for the payment by the reference stored before the card, its TransactionReference (Instruction, above). An answer gives the outcome: approved is ACSP, and declined is RJCT with AG07. A host’s “never received” is RJCT with AB11 only where the host documents that answer as final. Otherwise go to step 3.
  3. If the host cannot answer the enquiry, offers none, or gives a “not found” it does not document as final, reverse the payment. Send RJCT with AB11 once the host has confirmed the reversal, and not before (Which TransactionStatus to send, above).
  4. Keep trying steps 2 and 3 until one gives an answer, and send it as soon as it comes, however late: a late outcome replaces the UNKN the POS reads after the deadline. With the default settings, a host that answers lets the terminal report before the hold ends, 300 seconds from the instruction (Deadline, above). A host that does not answer leaves the POS reading UNKN until it does, and the outcome is then resent for 23 hours, as any outcome is (Resending is safe, above). A terminal that was off sends it on its first connection after.
  5. Never give up with nothing.

A refund is the same: a terminal that does not know whether a refund was made finds out by these steps, and sends RJCT with AB11 after a reversal only once the host has confirmed it.

A not_held outcome. The sale passed retention. Stop sending that outcome, keep it in the terminal’s own record, and leave reconciling it to an operator: the log holds what was sent.

A terminal_not_permitted outcome. The terminal is not paired, or its credential is retired, so the middleware kept what it said and did not take it. Keep the outcome, close the connection, and reconnect with the backoff: a connect refused 403 not_permitted backs off to one hour, and any other refusal is read by the holder’s table (What a holder of a dead certificate does, above). Once a connection is accepted, send the outcome again, as the resend path says.

The sign-in path. A terminal that declared SASQ holds no session at its fleet’s payment system when an Instruction arrives.

  1. Wake: turn the screen on, and bring the payment screen to the front over the lock screen.
  2. Make a fresh P-256 key pair in memory, sign its public key on a certificate’s connection, and send one LoginNeeded. Read its answer before sending another frame.
  3. On the LoginRequest, check its suite, open it and drop the private key. The terminal signs in at its fleet’s payment system with the opened SignedValue, and keeps the session.
  4. Send one LoginResponse naming the group’s LoginReference: SUCC, or FAIL with the code that fits. On a FAIL, ask again as Signing in, above, says.
  5. Take the payment, as the normal path does.
  6. On a Refusal of the ask, a LoginRequest that does not open, or no answer in 20 seconds, answer the sale RJCT with AB11, and ask again as Signing in, above, says for each.

Testing

In the middleware’s sandbox, whose start page is mw://start, also served as /docs/api/sandbox.md, with the sandbox’s address in $SANDBOX:

  1. Take a key with POST /sandbox/v1/keys, which needs no credential. Its 201 holds the key, shown once, your TesterIdentification, your world’s MerchantIdentification, and its nine terminals. Your terminal’s id is <tester>-yours, paired for your world’s vendor, and the key is a pos key of that vendor’s register, bound to the terminal.

  2. Connect your terminal under that id to $SANDBOX with its scheme made WebSocket’s, ws:// for http:// and wss:// for https://, then /v1/terminals/{POIIdentification}/connect, presenting the key on the upgrade as Authorization: Bearer sbx_... (Connect, above).

  3. Send it a sale as a POS would, naming that id, under the same key, with a new IdempotencyKey each time:

    curl -s -X POST "$SANDBOX/v1/sales" \
  -H 'Authorization: Bearer sbx_...' \
  -H 'Content-Type: application/json' \
  -d '{"MerchantIdentification":"sbx-3f9a1c2e7b10-M1","POIIdentification":"sbx-3f9a1c2e7b10-yours","SaleReferenceIdentification":"INV-1001","IdempotencyKey":"test-sale-0001","TransactionDetails":{"Currency":"AUD","TotalAmount":"12.50","SaleItem":[{"ProductDescription":"Flat white","ProductQuantity":2,"UnitPrice":"6.25","ProductAmount":"12.50"}]}}'

    with your key in place of sbx_..., and your TesterIdentification in place of sbx-3f9a1c2e7b10. The answer is 202, holding the sale’s TransactionReference. The terminal receives the instruction.

  4. Read the sale as the POS does, under the same key, until it settles:

    curl -s -H 'Authorization: Bearer sbx_...' \
  "$SANDBOX/v1/sales/sal_01970f6e7c3a7d3e8a4f2b1c9d0e1f2a?wait_seconds=25"

    with the TransactionReference from step 3. A read under another register’s key answers 404, as if the middleware never held the sale.

  5. Read the sale’s log with the read_log tool of the sandbox’s MCP server, given the TransactionReference. It answers every message of the sale both ways, with a fields_dropped line naming anything the middleware dropped from an outcome, so a terminal vendor can check it sends nothing extra. A sale to <tester>-approve, a simulated terminal, is a whole sale to compare against.

  6. To test signing in, connect as in step 2 with SASQ in Mw-Message-Functions, then send a LoginNeeded with a fresh key and no Signature, since a sandbox key’s connection has none (Signing in, above). Your world’s store holds the sandbox’s stand-in credential, sandbox_signed_value, KeyIdentification sandbox-signin-1, so the answer is a LoginRequest. Open it, and check the group’s Signature: the HMAC-SHA256 of Challenge’s ASCII bytes, keyed with the bytes of the sandbox’s published secret, in lowercase hex. mw://world and the start page give the secret, and the worked vector, in Signing in, above, checks your opening. Your world’s store holds none of AcceptorIdentification, UserName and ApplicationIdentification, so the group holds its four keys and its LoginReference alone. Then report it in a LoginResponse naming that LoginReference, as Signing in, above, says: the sandbox takes it as any middleware does.

A conformance run tests sign-in only on a terminal that declared SASQ when the step opened, in two steps: sign_in, with a credential attached, which starts the terminal asleep, its screen off and its application not in front, holding no session; and sign_in_none, for which the run ends the world’s attachment and restores it after, so the ask is refused sign_in_not_available. A terminal that did not declare SASQ is not tested on sign-in: each of those steps is not applicable, and its report row says so. A terminal that needs the middleware to sign it in must declare SASQ and run again. A run judges frames alone and sees no screen, so a green run does not prove that a terminal wakes.
