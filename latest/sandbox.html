Middleware: the sandbox

Last changed in v1.0.0.

The sandbox is a middleware of its own for testing a point of sale (POS) or a payment terminal against the middleware’s one schema, with no one from FUNDiMO in the room. It runs the same relay as live, beside simulated terminals, an MCP server for an agent, and conformance runs whose report is signed. You can go from nothing to a signed report from this document alone. An agent reads the same bytes through the sandbox’s MCP server as mw://start, and over HTTP as /docs/api/sandbox.md.

Nothing in the sandbox is a record. No card is charged and no money moves, and a world lasts 30 days. A live middleware refuses every sandbox key and every sandbox certificate, and the sandbox refuses every live credential.

Never send card, bank or personal data, here or on live: no card number, expiry, track data, card verification value, BSB, account number, cardholder name or other detail of a person. The middleware cannot detect one in a string you choose, and every message that passes through it is logged, with the ids that tie it to one sale. A key, a pairing code and a header value never reach a line.

In short

Changed in v0.6.0.

  1. Built against an earlier release? Read mw://changes, also served as /docs/api/changes.md: what changed in each release, newest first. Each page’s first line names the release of its last change, and each section changed since v0.2.0 names the release that changed it.
  2. Read /llms.txt, also served at /: the index of the middleware’s contracts, walks, field catalogue and conformance scenarios, which lists this page first.
  3. Read mw://environments, also served as /docs/api/environments.md: the two environments, the sandbox and staging, and each one’s base URL. Keep the base URL a setting from your first line of code.
  4. Take a key with POST /sandbox/v1/keys. It opens a world of your own (step 1).
  5. Add the sandbox’s MCP server with that key, then start a new session, or call it with curl in the session you are in (step 3).
  6. Learn the fields: mw://world, the describe_field tool and mw://fields.
  7. From your own code, send sales and refunds to your world’s simulated terminals as a POS (step 4), or take them on <tester>-yours as a terminal (step 5), and read both sides with read_log.
  8. Enrol for a certificate, run your side’s conformance scenarios, and keep the signed report (step 6).

The commands here read the sandbox’s address from $SANDBOX: the address this document was served from, with no path.

# The sandbox's address: /docs/api/environments.md gives its base URL. A name under `.invalid`
# never resolves: put the real one here.
SANDBOX=https://sandbox.mw.invalid

Every body the sandbox takes or gives is one JSON object in UTF-8, and every refusal it gives over HTTP has the body { "Error": { "Code": "...", "Message": "...", "Fields": [] } }. The 404 the sandbox’s gate gives for a path off its routes, and its 503 ca_unavailable when it has no CA, add "Next" beside Error, saying what to do, as a tool’s failure does. On enrolment, the edge in front of the sandbox, where it runs behind one, may also refuse, with a 429 of its own whose body is not an Error (Codes the sandbox adds). Where a table here says the normal backoff, wait 1 second, double the wait after each failure up to 30 seconds, and add a little randomness.

1. A key and a world

Changed in v0.5.0.

curl -s -X POST "$SANDBOX/sandbox/v1/keys"

No credential and no body are needed, and no contact detail is asked for or kept. The answer is 201:

{
  "SandboxKey": "sbx_...",
  "TesterIdentification": "sbx-3f9a1c2e7b10",
  "ExpiryDateTime": "2026-12-10T04:12:33Z",
  "MerchantIdentification": "sbx-3f9a1c2e7b10-M1",
  "RegisterIdentification": "reg_...",
  "Register": "server",
  "Terminals": { "approve": "sbx-3f9a1c2e7b10-approve", "decline": "sbx-3f9a1c2e7b10-decline", "technical": "...", "slow": "...", "late": "...", "silent": "...", "card": "...", "manual": "...", "yours": "sbx-3f9a1c2e7b10-yours" },
  "McpEndpoint": "https://sandbox.mw.invalid/mcp",
  "Enrolment": { "Role": "server", "PairingCode": "...", "Next": "Read mw://onboarding/server. This code lasts 15 minutes. POST /sandbox/v1/codes gives another." },
  "Next": "Add the MCP server with this key, then read mw://start. This key is shown once."
}
  • SandboxKey is your key, a pos key of your world’s register. It is shown this once, and the sandbox keeps only its digest, so a lost key is a new key and a new world. Send it as Authorization: Bearer sbx_..., and keep it out of logs and repositories, as any credential. You cannot end a key before its ExpiryDateTime. A key shown where others can read it, in a log, a repository or an agent’s session, opens your world alone and no live credential: treat it as spent, and take a new key for a new world.
  • TesterIdentification names you, and is no secret. Your world’s store and terminals are named after it.
  • ExpiryDateTime is when the key and the world end, 30 days on. After it the key is refused, and a new key is a new world.
  • MerchantIdentification is your world’s one store: every sale of yours names it.
  • RegisterIdentification is your world’s one register, which your key acts for. In a world of a server’s register, a server’s certificate names it in Mw-Register; in a world of a register on a device, your app enrols as it.
  • Register is your world’s kind, server or device.
  • Terminals are your world’s nine terminals (step 2).
  • Enrolment holds a pairing code for a pos server on your world, good 15 minutes (step 6). It is a secret, as the key is. In a world of a register on a device it holds no code (A world for a POS app on a device, below).

A world for a POS app on a device. A world’s one register is a server’s, which a POS on its own server names in Mw-Register, unless you ask for a register on a device: an app on a till that enrols as the register itself, with its own key and certificate, and sends no Mw-Register.

curl -s -X POST "$SANDBOX/sandbox/v1/keys" -H 'Content-Type: application/json' \
  -d '{"Register":"device"}'

The answer is the 201 above, with three differences: Register is device; RegisterIdentification is your register on a device, listed with the serial <tester>-register; and Enrolment holds no code, { "Role": "register", "SerialNumber": "sbx-3f9a1c2e7b10-register", "Next": "..." }. Your register takes sales on your key from the start, and asking for its code takes it off sale until your app enrols (4. The POS journey, step 8). A world keeps its kind for its life: to try both kinds of POS, take a key for each. With no body, a body that is not a JSON object, or no Register, the world is a server’s, as "Register": "server" asks; any other Register is 400 invalid_field, naming it, and no key is made, as is any other member, 400 unknown_field. A body past 1,024 bytes is not read, and gives a server’s world.

The sandbox’s TLS mode. mw://world’s TlsMode states which this sandbox runs. In direct, the mode of a sandbox with a CA on your own machine, the sandbox ends TLS itself, so a certificate it does not take can end the handshake with a TLS alert. In forwarded, the mode of a sandbox behind a load balancer, the load balancer ends TLS, no handshake fails on the certificate, and the refusal comes on the upgrade or the request instead. In off, plain HTTP, no handshake carries a certificate, and a sandbox with no CA issues none (step 6). The terminal contract’s table for a refused connection reads by it (/docs/api/terminal.md, What a holder of a dead certificate does).

2. Your world

Changed in v1.0.0.

Each terminal’s id is your TesterIdentification, a -, and a suffix. All nine terminals exist from the moment the key is issued, each is bound to your register, and your key may send a sale to any of them while your register is active, and read its sales whatever the register’s state: in a world of a register on a device, its code takes it off sale until your app enrols (4. The POS journey, step 8). Another tester’s ids answer as if they did not exist.

TerminalHeld byOn an instruction
-approveA simulatorAfter 500 ms: TransactionStatus ACSP, ResponseCode 00, AdditionalInformation APPROVED, TransactionDetails.AuthorisedAmount equal to the instruction’s TotalAmount, and a PaymentReference holding three card references under Card, made from the sale’s own TransactionReference, so each sale’s RetrievalReferenceNumber is its own, as a refund’s is
-declineA simulatorAfter 500 ms: RJCT with StatusReasonInformation.Reason AG07, ResponseCode 05, AdditionalInformation DECLINED
-technicalA simulatorAfter 500 ms: RJCT with Reason AB11: the terminal gave up and took no payment
-slowA simulatorAfter 8 seconds: as -approve
-lateA simulatorAfter the sale’s deadline plus 15 seconds: as -approve, so the sale reads UNKN, then ACSP
-silentA simulatorNever answers. The sale reads UNKN, and the terminal stays claimed for the hold. It declares neither SSAB nor SSMQ, so it is sent no StatusRequest, and an abort of its sale is 409 terminal_cannot_abort while the sale waits and through the hold; once the hold has ended, 409 sale_not_abortable
-cardA simulatorAfter 500 ms: as -approve, plus four fields a terminal must never send, a card number, an expiry, track data and a cardholder name, each a fixed test value. The middleware drops them before anything is logged or answered, and a fields_dropped line names each
-manualYou, through the MCP serverThe instruction waits for terminal_next_instruction, and you answer it with terminal_send_outcome. A StatusRequest and an Abort wait there too. Eight wait at most, of the three kinds together: a ninth is not kept, and a sale whose instruction was not kept ends UNKN
-yoursYour own terminalWhatever your terminal and its own host do: the sandbox simulates no card host behind it (step 5). A sale to it while it is not connected is 409 terminal_offline. A LoginNeeded from it is answered under your store’s sign-in stand-in, below

A POS reads a sale’s TransactionStatus: PDNG while it waits, then ACSP, RJCT with its StatusReasonInformation, or UNKN when no outcome came by the deadline. An UNKN sale may still settle, so keep reading it. mw://world states the timers in force: how long a sale waits for its outcome, from the sale; how long a terminal whose sale went UNKN stays claimed, from the sale’s deadline, so 75 seconds from the sale here; how long a sale is kept; and how often the middleware sends a connected terminal a WebSocket Ping.

Every simulated ACSP states the amount. A simulator that approves sends TransactionDetails.AuthorisedAmount, the instruction’s TotalAmount as it came, as the terminal contract asks (/docs/api/terminal.md, Outcome), so the sale reads it back beside TotalAmount, equal to it. A bill of 50.00 with a store’s 15% public holiday surcharge on it is a sale of 57.50, and -approve approves it with "AuthorisedAmount": "57.50". An RJCT states none, since no payment was taken. An outcome sent again, after a reconnect or as the answer to a StatusRequest, states the same amount. -manual sends the outcome you write, so state the amount in it yourself.

Every simulated terminal takes refunds. Each says so on its upgrade, Mw-Transaction-Types: CRDP, RFND, and answers a refund as the table says it answers a sale, after the same wait: -approve refunds it, ACSP with TransactionDetails.AuthorisedAmount equal to the refund’s own TotalAmount and card references of the refund’s own, never the sale’s; -decline declines it, RJCT with AG07; -technical gives up, RJCT with AB11, and no refund is made; -silent never answers, so the refund reads UNKN; -card adds its four fields, which the middleware drops; and -manual queues the instruction, with TransactionType RFND and the sale under OriginalTransaction, for terminal_next_instruction. -yours takes a refund only once your terminal declares RFND on its upgrade (step 5). mw://world’s Refunds says the same of each of your terminals.

Every simulated terminal but -silent answers a StatusRequest. Each says so on its upgrade, with SSMQ in Mw-Message-Functions: SSAB, SSMQ, keeps the outcome of each sale and refund for 24 hours, its last 64, and answers as the terminal contract says (/docs/api/terminal.md, StatusRequest). Asked about a sale whose outcome it keeps, it sends that outcome, at most once on a connection. Asked while the payment runs, it sends nothing, and the outcome once the payment ends. Asked about a sale it never received, it sends RJCT with AB11 when what it keeps reaches back further than SecondsSinceInstruction, keeps that as the sale’s outcome, and answers an instruction of the sale that comes later with it; when it does not reach back that far, it sends nothing. A second instruction while a payment runs starts nothing: it gets RJCT with AB11, and the payment running finishes as before. -manual keeps a StatusRequest for terminal_next_instruction, and you answer it with terminal_send_outcome, or not at all. -silent declares nothing, so it is never asked. mw://world’s StatusRequests says the same of each of your terminals.

Every simulated terminal but -silent answers an Abort. Each says so on its upgrade, with SSAB in the same header, and answers as the terminal contract says (/docs/api/terminal.md, Abort), when your POS cancels a sale or a refund with POST /v1/sales/{TransactionReference}/abort. An Abort of a payment still waiting stops it: the terminal sends RJCT with StatusReasonInformation.Reason DS02, once, and never the outcome its wait would have ended in, so the sale reads RJCT with DS02. -slow’s 8 seconds leave the time to try it, and so does -late’s wait, past the deadline too until the hold after it ends, where the DS02 replaces the UNKN the sale reads. -late answers 15 seconds after the deadline, so with a hold shorter than that, an abort once the hold has ended is 409 sale_not_abortable; mw://world states both timers. A payment whose wait has ended is with its host and is not stopped: the terminal sends the outcome it keeps for the sale, at most once on a connection, and never DS02. For a sale it never received, it sends nothing. An Abort stops only the payment it names. -manual keeps an Abort for terminal_next_instruction, and you answer it with terminal_send_outcome: RJCT with DS02 if you stop the payment. -silent declares neither, so an abort of its sale is 409 terminal_cannot_abort while the sale still holds the terminal, as it waits and through the hold. The middleware reads the sale’s state before the terminal’s connection, so once the hold has ended the abort is 409 sale_not_abortable. mw://world’s Aborts says the same of each of your terminals.

Your store holds a sign-in credential: the sandbox’s stand-in. A terminal that needs a session at its fleet’s own payment system asks the middleware for what that system takes for a sign-in (/docs/api/terminal.md, Signing in). Your world’s store holds, from the moment the key is issued, the sandbox’s stand-in for a fleet’s credential: Adapter sandbox_signed_value and KeyIdentification sandbox-signin-1. It signs under your world’s fleet’s sign-in profile, which the key’s issue sets with it: ApplicationIdentification null, and the Profile Algorithm HMAC-SHA256, ChallengeLength 32, ChallengeEncoding hex and SignatureEncoding hex, until your back office sets another, which mw://world then states. It signs with the sandbox’s own secret, which is published here and in mw://world and so proves nothing to any fleet: mw-sandbox-signin-secret-published-not-secret, its bytes as written (SecretEncoding text). So your terminal can verify the Signature of the group it opens: under the profile your world comes with, the HMAC-SHA256 of the Challenge’s ASCII bytes, keyed with those bytes, in lowercase hex (step 5). No fleet’s secret is ever set in the sandbox. mw://world’s SignIn states what your store holds now, each read counted among your tool calls a minute: the stand-in’s Adapter and KeyIdentification, the published Secret with its SecretEncoding beside it, and your world’s fleet’s ApplicationIdentification and Profile. A world opened before the sandbox gave each world its stand-in holds none, and a new key opens a world that does. The simulated terminals never ask.

Your world’s back office. POST /sandbox/v1/codes with {"Role":"admin"} under your key gives the code of an admin server of your world’s vendor, in a world of either kind. Its certificate reaches the routes of /docs/api/openapi-admin.yaml inside your world, and /docs/api/back-office.md, Trying it in the sandbox, walks a back office’s first steps there. Your world’s vendor is a fleet and a POS vendor at once. What your world came with, its store, its nine terminals, its register and its sign-in stand-in, is read-only there: a write to one of them is 409 sandbox_read_only. Make your own: a store, a terminal, a register, and a sign-in credential with POST /v1/vendors/{VendorIdentification}/signin-credentials. Your world’s vendor holds at most 60 of each kind of object, what your world came with and removed ones counted: a create past that is 409 sandbox_object_limit (7. Codes the sandbox adds). Your back office sends at most 240 writes an hour: one past that is 429 sandbox_rate. A vendor a body names must be your own: another is 403 not_permitted. Your back office’s log lines are kept apart from your world’s others, so a back office that polls takes nothing from a run’s lines. A sandbox whose TLS mode is off takes no certificate, so a world there has no back office.

The simulators connect on your world’s first request, which waits up to 2 seconds for them. A world with no call for 30 minutes has them closed, and the next request connects them again, keeping nothing: asked about a sale made before, they send nothing.

3. The MCP server

Changed in v0.5.0.

claude mcp add --transport http mw-sandbox "$SANDBOX/mcp" --header "Authorization: Bearer sbx_..."

The command keeps the key in that client’s configuration. Then start a new session: a client reads its servers when a session starts, so an agent cannot give itself the key in the session it is in. Any MCP client on revision 2026-07-28 or 2025-11-25 will do, over Streamable HTTP at POST /mcp, with the key on every request. There is no session and no OAuth.

Or call it over plain HTTP, which needs no new session and puts the key in no client’s config. Keep the one line Authorization: Bearer sbx_..., with your key, in a file only you can read, anywhere outside a repository, such as ~/.mw-sandbox-auth, which the commands below use. Send each request on its own, with no initialize before it. In bash or zsh, the first line makes the file yours alone, at the second paste the key and press Enter, and the curl is any request, here your world:

touch ~/.mw-sandbox-auth && chmod 600 ~/.mw-sandbox-auth
(read -rs key && printf 'Authorization: Bearer %s\n' "$key" > ~/.mw-sandbox-auth)
curl -s "$SANDBOX/mcp" -H @"$HOME/.mw-sandbox-auth" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2025-11-25' \
  -d '{"jsonrpc":"2.0","id":1,"method":"resources/read","params":{"uri":"mw://world"}}'

The key is not shown as you paste it. read and printf are the shell’s own, and curl reads the header from the file, so the key is in no argument a process list shows and no line of your shell’s history.

  • With no key, every resource but mw://world can be read, and describe_field, validate_message and explain_refusal answer. Every other tool answers key_required, with the curl line in Next.
  • A key of the sbx_ shape that is unknown or past its expiry is answered key_not_recognised by every tool that needs a key, with how to get a new one in Next. mw://world read under such a key is JSON-RPC -32602, its data {"Code": "key_not_recognised", "Next": "..."} with the same Next.
  • Any other credential, a token, Basic, or a live credential, is 401 credential_not_for_sandbox on every request. If it was a live credential, rotate it.

The release the sandbox runs. The answer to initialize names the release of the middleware this sandbox runs, in serverInfo.version and in the first sentence of instructions. GET /v1/health names it too, in Version, and needs no key. The MCP server states its own release and reads no other: it never calls staging. Staging’s own GET /v1/health names the release staging runs, at the base URL mw://environments gives.

6. Conformance

Changed in v1.0.0.

A run walks its side’s scenarios in order, ten for a POS, thirteen for a terminal, five for a fleet’s back office and four for a POS vendor’s, one step at a time, and judges each from the log alone. Each step has 300 seconds. mw://conformance, also served as /docs/api/conformance.json, holds every assertion and what to change when one fails.

  • A run needs a certificate. A sandbox key cannot start one: conformance_start answers certificate_required until your side has enrolled (step 4 or 5, and for a back office /docs/api/back-office.md, Trying it in the sandbox). A run judges what one certificate sends: on Side: pos, the newest live certificate of your world’s pos servers, or, in a world of a register on a device, the register’s; on Side: terminal, -yours’s; and on Side: fleet and Side: pos_vendor, the newest live certificate of your world’s admin servers, in a world of either kind. So a run needs a sandbox that issues certificates: one with a CA, in TLS mode direct or forwarded, as one behind a load balancer is. A sandbox started with TLS off and no CA, as a local one may be, issues none: its POST /v1/enrol answers 503 ca_unavailable with a Next saying so, and no run can start on it. Everything else here works on a key alone.
  • A run judges your world’s log. Your world’s log holds at most its newest 2,000 lines, and at most 1 MiB of them, the oldest out first, and a step reads only the lines that came after it opened. Older lines leaving it change nothing. A step whose own lines left it before they were judged, because your key wrote more than that during the step, is undetermined, and the ended run’s Note says how many lines and to run it again with less traffic. A new key is a new, empty log, and so is 30 minutes with no request of yours. A back office’s run reads your back office’s own log instead, which holds your admin servers’ lines alone, within the same bounds, so your other traffic takes nothing from it.
  • Only your own integration counts. A line counts only when it bears your certificate, so traffic from this MCP server, send_sale among it, does not.
  • A terminal run’s sales are yours. On Side: terminal the sandbox sends each step’s sale as your POS, and it counts as one of your sales a minute, beside your own and send_sale’s. While the minute is full, Note says so and the sale waits. A resend of it is not counted again.
  • Verdicts. Each assertion is pass, fail or undetermined, and one the log cannot decide, because lines were lost or a word is unknown, is undetermined, never pass. A run is green only when it is complete, every scenario is pass or not_applicable, no line was lost while it ran, and none of a step’s own lines was evicted.

conformance_report gives { "Report": "<JSON text>", "Signature": "<base64>", "KeyIdentification": "<16 hex>" }. The signature is Ed25519 over the exact bytes of Report, in standard base64 with padding, and mw://report-key holds the public key it verifies with, and its KeyIdentification, the key’s first 8 bytes in lowercase hex. PublicKey is the raw 32-byte Ed25519 key in standard base64, not a PEM or DER structure. To check a report kept in report.json with OpenSSL 3 or later, put the key in a PEM file first: its DER is the fixed 12 bytes 302a300506032b6570032100 and then the key, and since 12 bytes are exactly 16 base64 characters, MCowBQYDK2VwAyEA, the PEM is that text and then PublicKey:

KEY='...'  # mw://report-key's PublicKey
printf -- '-----BEGIN PUBLIC KEY-----\nMCowBQYDK2VwAyEA%s\n-----END PUBLIC KEY-----\n' "$KEY" > report-key.pem
jq -j .Report report.json > report.txt
jq -r .Signature report.json | base64 -d > report.sig
openssl pkeyutl -verify -pubin -inkey report-key.pem -rawin -in report.txt -sigfile report.sig

It prints Signature Verified Successfully and exits 0 when the report is the sandbox’s, and exits 1 when one byte of Report differs. jq -j writes the text of Report with no newline after it, so the bytes are the ones signed. As with any check of a signature, a pass says the report is the sandbox’s, not that the run was green: read Result in Report for that.

A report shows what a holder of your certificate sent. It does not identify a product or a vendor, ProductName and ProductVersion are as declared, and no card, host or acquirer took part: it is not a card scheme’s certification. A POS’s or a terminal’s report says the far side was simulated, and a restart was simulated for you alone. A back office’s says in Simulated “FUNDiMO’s part was the sandbox’s: it listed the admin server when asked.” and “The lost answer was staged for this tester.”

ContractVersion in a report is the family of paths the run’s routes were under: v1, as in /v1/sales on the relay and /sandbox/v1/keys on the sandbox. It is not the release. It moves only when the middleware serves a new family of paths, so many releases may share one ContractVersion. To compare two reports, compare their SandboxVersion.

SandboxVersion is the release of the middleware that ran the run. A run lives in one process of the sandbox and is lost when the sandbox restarts, so one run never spans two releases.

The sandbox keeps your 32 newest runs, the one running among them: a 33rd run lets the oldest ended one go as it starts. Within those 32, an ended run is kept at least 24 hours after it ends; once 24 hours have passed since your last run ended, all of them may go. A restart loses every run. A run gone any of these ways is run_not_found. Keep each report you need with conformance_report once its run ends.

ReportVersion counts the report’s own shape, not the release.

What a green run does not check

Changed in v1.0.0.

A green run proves your integration did what each step asked, once. It cannot see what your code would do on a day no step stages, so each rule below binds you and no scenario checks it. Each is stated where the link says.

For a POS:

  • UNKN tells the cashier to check the terminal before another tender, as soon as the sale reads UNKN, while it keeps reading: not only once reading gives up. UNKN means a payment may have been taken (/docs/api/openapi-pos.yaml, Sale’s TransactionStatus).
  • A 404 sale_not_found on an id the middleware gave you reads as unknown, not as no sale (/docs/api/openapi-pos.yaml, readSale’s 404).
  • 409 idempotency_conflict after a lost answer reads as unknown: a sale may exist under that key, so the cashier checks the terminal before another tender (/docs/api/openapi-pos.yaml, createSale’s 409).
  • A field you do not know is ignored, and a TransactionStatus you do not know reads as UNKN (/docs/api/openapi-pos.yaml, Sale).
  • No card, bank or personal data in any string you choose, an item’s description or an invoice reference among them (the top of this page, and /llms.txt).
  • The people who use your POS are your responsibility. The middleware takes it that a user of your POS was authenticated to make each sale and refund, and judges nothing about that user (/docs/api/openapi-pos.yaml, info).

For a terminal:

  • Store the TransactionReference before taking the card, and the Outcome before sending it, somewhere a crash or a reboot does not lose (/docs/api/terminal.md, In short, and Resending is safe).
  • One payment at a time. An Instruction that arrives while a payment is open is not started and not queued: it is answered RJCT with AB11, and the payment that is open finishes as before (/docs/api/terminal.md, One payment at a time).
  • A repeated Instruction never charges twice, after a restart of the terminal as well as within one run of its code (/docs/api/terminal.md, The paths, step by step).
  • RJCT with AB11 only when no payment was taken: decided from what the terminal and its host did, never from what a step is called (/docs/api/terminal.md, Which TransactionStatus to send).
  • A frame the middleware refused is kept aside and not sent again but as the Refusal section says, across reconnects as well (/docs/api/terminal.md, Refusal).
  • An Abort stops only a payment not yet with its host. A green run does not prove the rest of the contract’s abort: that a terminal whose payment is already with its host carries on and sends the host’s outcome, never DS02; that an Abort for a reference whose payment ended is answered with that outcome, unless the terminal already sent it on this connection; that one for a reference the terminal holds no record of is answered with nothing; that it sends DS02 only in answer to an Abort, and AB11 for a cancel at the terminal; and that an Abort never stops a payment for another reference (/docs/api/terminal.md, Abort). cancel stages one case, a payment held with no card presented, and judges that the terminal declared SSAB and answered the Abort with RJCT and DS02, once.
  • A sale’s outcome goes at most once on each connection, and again only after a reconnect, never on a timer (/docs/api/terminal.md, Resending is safe). A run fails a repeat it sees inside a step’s 3-second hold, <scenario>.one_outcome, and does not see a slower one. The log names no connection, so a run cuts your terminal’s lines into connections at each connect and disconnect: a repeat that straddles one of those lines as one connection replaces another goes unseen, and an outcome your old connection was still sending as your new one connected can read as a repeat on the new one, which ends a run red that should not be, never green, and can pass when run again. Under a lost or evicted line a repeat reads undetermined.
  • A person reaches your app’s enrolment screen from the app’s own menu or settings, with the device alone and again after the first enrolment, and the screen meets the rest of its requirements (/docs/api/onboarding-device.md, The enrolment screen). A run sees the connection your terminal holds on its certificate, never the screen it was enrolled on.
  • Check the sandbox’s server certificate, and the middleware’s in live, against your trust store, as any HTTPS or WSS client does. Never turn the check off: a terminal that does would send its outcomes to whoever answers at the address. A local sandbox may present a certificate under a root of its own, which you add to your trust store; one behind a load balancer presents a public certificate. Whoever started a local sandbox has its root certificate and gives it to you; the sandbox does not serve it, since a root fetched over the connection it vouches for proves nothing.

For a back office:

  • A code goes to the installer, by a path no one else reads, and stays out of every log, your back office’s own among them (/docs/api/back-office.md, A fleet’s back office, in order, step 3). A run reads the log, where a code reads <withheld>, so it cannot see where yours went.
  • A 503 or a 429 is retried on the normal backoff, and Retry-After is kept where an answer gives it. A create goes again under the same IdempotencyKey, and after any other write the object is read back first (/docs/api/back-office.md, Retrying a create, and Refusals).
  • A listing is read to its last page, until NextPage is null, and a row missing from a page is never taken for one that is gone (/docs/api/back-office.md, Reading a list a page at a time). terminal_listed passes on any page that names the terminal.
  • A 403 stops the act it answers. not_permitted is one code for every reason, a suspension among them, so your back office does not send the same request again on a timer, and a person asks FUNDiMO (/docs/api/back-office.md, When FUNDiMO suspends your vendor, or cancels a go-live).
  • A removed terminal is never asked again. removed has no exit, so your back office asks no code or state of it again, and a device listed afresh is a new terminal, under a new POIIdentification (/docs/api/back-office.md, A fleet’s back office, in order, step 11).
  • Each alias a fleet proposes is decided: a POS vendor’s back office accepts or rejects it within its 14 days. A world is one vendor, so no other vendor proposes one there, and no step stages one (/docs/api/back-office.md, A POS vendor’s back office, in order, step 5).

What the sandbox never does

Changed in v1.0.0.

  • Show one tester’s data to another. Every tool and route reads your world alone, from your key or your certificate, and another tester’s sale answers as one that never existed.
  • Accept a live credential. Its store holds no live row, a live certificate is refused, and a non-sbx_ bearer at /mcp is 401.
  • Keep a card or personal field. The allow-list drops what a terminal must not send before any line is written, and no tool keeps what it checks.
  • Let a tool change a credential. Keys come from the plain routes under /sandbox/v1/ alone, and codes from those and from your back office’s own routes, never from a tool.
