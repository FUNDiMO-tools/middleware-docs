Middleware: onboarding a device

Last changed in v0.5.0.

This is the walk for a vendor writing an Android app for a SUNMI device: a payment terminal, or a register, which is a POS app on a device. It is written for that maker’s devices today; other makers’ devices are intended, each with a walk of its own. It goes from registering the app with the middleware to a certificate the app renews by itself, with Kotlin to paste at each step on the device, and says what the app’s enrolment screen must be and how a person reaches it (The enrolment screen). You can build the device’s side from this document alone. An agent reads the same bytes through llms.txt, and through the sandbox’s MCP server as mw://onboarding/device.

A live device proves who it is with a client certificate from the middleware’s own CA. Its key is made in the Android keystore and never leaves it. The middleware issues the certificate once the device shows three things: a pairing code an installer typed or scanned, which proves an authorised person is at the device now; the serial its listing holds; and an Android Key Attestation chain, which proves the key is in hardware, on an unmodified device of an allowed model, held by the app its vendor registered. Nothing is given to a vendor to embed in an app. The certificate lasts 30 days and renews from day 15 with a new key. FUNDiMO’s staging middleware can be set to issue it though some checks of the attestation fail, for testing, and to mark the device so (step 3, Which devices the middleware admits).

Read it beside docs/api/terminal.md, the terminal’s contract. A vendor with a server reads docs/api/onboarding-server.md instead, and linking a register to a terminal at the counter is docs/api/linking.md. docs/api/openapi-terminal.yaml holds the schema of every route a device calls here, and docs/api/openapi-pos.yaml holds those a register calls, with the two that list a register and give it a code. The three routes that register an app, list a terminal and give it a code are in the Operator API, which FUNDiMO gives a vendor with an admin server directly. The middleware publishes no Android library: the code here is for you to paste and own.

What is proven on a device, and what is not yet

Every step here was written from documents. Two runs have since tried parts of it on one SUNMI P2 Lite SE, Android 11 (API 30), whose keystore is software: AOSP’s software keymaster keeps its keys, and no trusted environment was found behind Android’s keystore. FUNDiMO’s bench, run from 12-Nov-2026, ran on the device alone, with no network and no middleware. A terminal vendor’s trial on 13-Nov-2026 enrolled in the sandbox on its first attempt and connected on its certificate. The sandbox requires no attestation, so neither run proves a live enrolment. Each step that rests on something only a device can confirm says so, by the bench item it rests on: proven on a device, and on which, or not yet proven on a device. Each item not yet proven is checked on a SUNMI device before the first live enrolment, and this walk is not final until BENCH-2 is.

In short

Changed in v0.5.0.

  1. The vendor registers the app’s package and signing digest for its role (step 1).
  2. The terminal’s fleet owner, or the POS vendor for a register, lists the device by its serial, and gives the installer the pairing code the middleware answers with (step 2).
  3. On the device, the app takes the code’s five words, as the installer types them or scans them from a QR code (step 2), reads the serial (step 5), makes a P-256 key in the Android keystore with the enrolment challenge (step 3), builds a CSR for it (step 4), and sends all of it to POST /v1/enrol (step 6).
  4. It keeps the CertificateChain the middleware answers with against the key’s alias (step 7), and presents the key and the chain at the TLS handshake of every call after, REST and WebSocket alike (step 8).
  5. Once a day it asks GET /v1/certificates/self (step 9). When RenewNow is true, it renews with a new key under a new alias, or sends again as it was a renewal still waiting for a verdict, and deletes the old key only after a call on the new one has been answered (step 10).
  6. After a refusal it does what the holder’s table says, and never deletes its key (What a holder of a dead certificate does). A device off longer than its certificate re-enrols with a new code (step 11).
  7. A person enrols the device on the app’s enrolment screen, which an entry of the app’s own menu or settings opens, with the device alone, and again after the first enrolment (The enrolment screen).

In the sandbox

Changed in v0.5.0.

The same file is served in the sandbox, where five things differ.

  • The sandbox’s gate answers 404 to the operator’s routes. In their place the sandbox has two routes of its own, served by its own process, mw-sandbox (the middleware’s 003b-sandbox), under your tester’s sandbox key, and a live middleware has neither: POST /sandbox/v1/app-identities registers the app (step 1), and POST /sandbox/v1/codes gives the code (step 2).
  • A register is tried in a world of its own kind, which POST /sandbox/v1/keys with {"Register":"device"} opens (docs/api/sandbox.md, 1. A key and a world). Its register is listed with the serial <tester>-register, as every world’s own terminal is -yours with <tester>-yours.
  • No attestation is required, so an emulator or a debug build can enrol. A chain sent is checked all the same, for its key, its challenge and its app, against app identities where a debug build counts, so you can prove your package and signing digest before you have a device. The first live enrolment is where the rest is proven.
  • Enrolment needs a sandbox with an issuing certificate. A sandbox run without one answers POST /v1/enrol with 503 ca_unavailable.
  • A code can make a certificate due at once: POST /sandbox/v1/codes with "Due": true beside Role gives a code whose certificate is issued 16 days back, so RenewNow is true from its first daily check, and renewal, the overlap and their refusals can be tried the same day (docs/api/sandbox.md, 4. The POS journey).

What you need

  • An Android app on the device. setAttestationChallenge needs API 24, and setDevicePropertiesAttestationIncluded, which puts the device’s brand and model in the attestation, needs API 31.
  • OkHttp, com.squareup.okhttp3:okhttp, for every call.
  • Bouncy Castle’s PKIX library, org.bouncycastle:bcpkix-jdk18on, to build the CSR. Only its CSR classes are used, and it is not installed as a security provider. It brings bcprov-jdk18on, which holds class files for Java 9 and later. A toolchain that cannot read them fails with Unsupported class file major version 59, as Android Gradle Plugin 4.2 with Jetifier does: there, take org.bouncycastle:bcpkix-jdk15to18, the same classes built for Java 5 to 8.
  • WorkManager, androidx.work:work-runtime-ktx, for the daily check, or any scheduler the app already has.
  • Android’s own org.json, for bodies.
  • The middleware’s word list, docs/api/words.txt, in the app’s resources, to read a code (step 2).
  • The middleware’s base URL, one of those /docs/api/environments.md names, kept in a setting, which the helpers below read as MW.

/** What the middleware answered: a 2xx and its body, or a refusal and its `Error.Code`. */
sealed interface Answer {
    data class Ok(val status: Int, val body: JSONObject) : Answer
    data class Refused(val status: Int, val code: String?) : Answer
}

/**
 * Sends [request] and reads the answer. Throws `IOException` where no answer came: a close, a
 * reset, a timeout, or a handshake that failed.
 */
fun call(client: OkHttpClient, request: Request): Answer =
    client.newCall(request).execute().use { response ->
        val text = response.body?.string().orEmpty()
        if (response.isSuccessful) {
            Answer.Ok(response.code, JSONObject(text.ifEmpty { "{}" }))
        } else {
            val code = runCatching { JSONObject(text).getJSONObject("Error").getString("Code") }
            Answer.Refused(response.code, code.getOrNull())
        }
    }

/**
 * Sends [request] until an answer comes, waiting 1 second, then twice as long each time up to
 * 30 seconds, with a little randomness. Only for a body that is safe to send again: enrolment
 * and renewal answer a repeat with what they already issued.
 */
fun sendUntilAnswered(client: OkHttpClient, request: Request, tries: Int = 5): Answer {
    var wait = 1_000L
    repeat(tries - 1) {
        try {
            return call(client, request)
        } catch (noAnswer: IOException) {
            Thread.sleep(wait + Random.nextLong(wait / 2))
            wait = minOf(wait * 2, 30_000L)
        }
    }
    return call(client, request)
}

/** DER bytes as PEM, 64 characters a line. */
fun pem(label: String, der: ByteArray): String {
    val body = Base64.encodeToString(der, Base64.NO_WRAP).chunked(64).joinToString("\n")
    return "-----BEGIN $label-----\n$body\n-----END $label-----\n"
}

/** Bytes as lowercase hex. */
fun ByteArray.hex(): String =
    joinToString("") { (it.toInt() and 0xff).toString(16).padStart(2, '0') }

/** 64 lowercase hex characters as 32 bytes, or null. */
fun bytesOfHex(text: String): ByteArray? {
    if (text.length != 64 || !text.all { it in '0'..'9' || it in 'a'..'f' }) return null
    return ByteArray(32) { text.substring(it * 2, it * 2 + 2).toInt(16).toByte() }
}

1. Register the app identity

Changed in v0.4.0.

A device enrols only if the app holding its key is one its vendor registered. The middleware learns which app holds the key from the attestation, which states the app’s Android package and the SHA-256 of each certificate the app is signed with, so nothing secret is put in the app. Register each app once for its role: terminal for a payment terminal’s app, register for a POS app on a device.

One app holds one role. One device may run both, a payment terminal’s app and a POS app: two apps, each registered for its own role, and two principals, each with its own listing, code, key and certificate. Both listings may carry the device’s one serial, and the middleware keeps their codes apart. Each app enrols with its own principal’s code. Where the app sends its attestation, as production requires, the other app’s attestation on a code is refused 403 app_identity_unknown. An enrolment with no attestation is not checked for its app: in the sandbox, and on a middleware set to mark, it enrols as whichever principal the code and serial name, so the enrolment screen says which app a code is for. In the sandbox the two serials differ, <tester>-yours and <tester>-register, so a code sent with the other app’s serial is 403 code_not_valid. A row of the operator’s allowed list admits a model for one vendor or for every vendor, so a model allowed for a fleet alone does not admit a POS vendor’s register on the same device: ask for it for each vendor, or for every vendor (Which devices the middleware admits). A middleware set to mark records the model’s check rather than refusing.

On live, the operator or the vendor’s own admin sends POST /v1/vendors/{VendorIdentification}/app-identities (in the Operator API, which FUNDiMO gives a vendor with an admin server directly), with this body:

{ "Role": "terminal", "AppPackage": "au.com.example.terminal", "SigningDigest": "..." }

In the sandbox, POST /sandbox/v1/app-identities takes the same body under your tester’s key, with $SANDBOX the sandbox’s address:

curl -s -X POST "$SANDBOX/sandbox/v1/app-identities" \
  -H 'Authorization: Bearer sbx_...' \
  -H 'Content-Type: application/json' \
  -d '{"Role":"terminal","AppPackage":"au.com.example.terminal","SigningDigest":"..."}'

The answer is 201:

{ "AppIdentification": "app_...", "Role": "terminal", "AppPackage": "au.com.example.terminal", "SigningDigest": "...", "Debug": true, "State": "active" }

The digest is of the certificate that signed the app as it is installed on the device. If a store re-signs your app, it is the store’s certificate, not your upload key’s. Register a debug build’s digest apart, as a debug build. To read the digests from the app itself:

import android.content.Context
import android.content.pm.PackageManager
import java.security.MessageDigest

/** The SHA-256 of each certificate this app, as installed, is signed with. API 28 and later. */
fun signingDigests(context: Context): List<String> {
    val info = context.packageManager
        .getPackageInfo(context.packageName, PackageManager.GET_SIGNING_CERTIFICATES)
    val signers = info.signingInfo?.apkContentsSigners ?: return emptyList()
    return signers.map { MessageDigest.getInstance("SHA-256").digest(it.toByteArray()).hex() }
}

Two rules of the attestation follow from this step. The app must be the only package holding the key: an app sharing its user id with another package, by android:sharedUserId, shares its keys with it, the attestation then names more than one package, and that is refused. And every digest the attestation states must be registered, so an app signed with two certificates registers each. A device whose app is not registered is refused 403 app_identity_unknown at enrolment and at renewal.

2. The listing and the code

Changed in v0.4.0.

Every device starts with one human act. On live, the terminal’s fleet owner lists it at a store by its serial, POST /v1/merchant-stores/{StoreIdentification}/terminals (in the Operator API, which FUNDiMO gives a vendor with an admin server directly), and the POS vendor’s admin lists a register by its serial, POST /v1/registers (in docs/api/openapi-pos.yaml, as listRegister, tagged registers). The 201 holds the device’s id, POIIdentification or RegisterIdentification, and its PairingCode:

{ "POIIdentification": "poi_...", "SerialNumber": "SN-0001", "State": "listed", "PairingCode": "bronze.farm.loop.prism.tempo" }

The code is five different words of the middleware’s word list, in lower case and joined by dots, valid 15 minutes and for one use, and shown this once. It is a secret: the listing party gives it to the installer, read aloud, sent, or shown as a QR code (The QR code, below), and the installer types or scans it into your app’s enrolment screen at the device (The enrolment screen). It is kept out of every log, the app’s own among them. A fresh one comes from POST /v1/terminals/{POIIdentification}/pairing-code, which also re-pairs a paired terminal and is in the Operator API, or for a register from POST /v1/registers/{RegisterIdentification}/pairing-code, in docs/api/openapi-pos.yaml.

In the sandbox the listing is done for you: your tester’s world holds a terminal of your own, -yours, listed with the serial <tester>-yours. POST /sandbox/v1/codes gives its code, under your tester’s key:

curl -s -X POST "$SANDBOX/sandbox/v1/codes" \
  -H 'Authorization: Bearer sbx_...' \
  -H 'Content-Type: application/json' \
  -d '{"Role":"terminal"}'

The answer is 201:

{ "Role": "terminal", "PairingCode": "bronze.farm.loop.prism.tempo", "SerialNumber": "sbx-...-yours", "Next": "..." }

Enrol with that code and that SerialNumber within 15 minutes. A new code re-pairs -yours, so its sandbox key is refused on its upgrade until it enrols. Past 6 codes an hour the route answers 429 sandbox_rate.

A register is tried in a world of its own kind (In the sandbox, above), where {"Role":"register"} gives your world’s register’s code and its SerialNumber, <tester>-register. It re-pairs the register, so the register takes no sale until it enrols. A world’s kind does not change: a world of a server’s register answers {"Role":"register"} with 400 invalid_field.

The word list

The list is docs/api/words.txt: 1,024 words, one a line, each 3 to 6 letters a to z. The sandbox serves it as /docs/api/words.txt, and its MCP server as mw://docs/words.txt. Each word is named by its first four letters: no two words share them, and none begins another, so an app can complete a word from its first letters, by the fourth at the latest, and a word of three letters at its third. No word is one said for a separator, as dot or dash would be, so a code read aloud is five words and nothing between them.

Put the list in the app as src/main/resources/words.txt, so the app and its unit tests read the same bytes. The SHA-256 of the list as published is e6104a521cec9b0224c1dfa51e6fceefcb7f5e0e4cd36adb168e15fa92686d5a: check your copy against it.

Typing the code

The middleware reads a device’s code one way, and the app reads it the same way before it sends, so a code the middleware would refuse never leaves the device. The middleware takes:

  • at most 64 characters;
  • spaces, tabs and line ends before the first word and after the last, which it drops, since a scanner often ends its text with a line end;
  • one or more dots, spaces or hyphens between two words, mixed as typed;
  • the letters a to z in either case, read as lower case, and no other letter;
  • and then five words of the list, all different.

Anything else is 400 invalid_field naming PairingCode, before any code is looked up, so it costs no attempt. The middleware completes no word: bron is not bronze. Completing a word is the app’s, so the app sends the whole words, and computes the challenge from them.

What the app does:

  • Its field turns off the keyboard’s own corrections and suggestions, with InputType.TYPE_CLASS_TEXT or InputType.TYPE_TEXT_VARIATION_VISIBLE_PASSWORD, so the keyboard does not change one word into another.
  • Once the letters typed begin one word of the list alone, it completes the word and its dot, and the fifth word without its dot: a dot or a hyphen after the last word is refused.
  • A letter that begins no word is shown at once, so a misheard word costs a retype, not an attempt.
  • It lowers case with lowercase(Locale.ROOT). On a device set to Turkish, the device’s own locale lowers I to a dotless ı, and PRISM would read as no word.
  • It sends the code as the middleware shows it, bronze.farm.loop.prism.tempo, as deviceCode returns it, and computes the challenge from the same text (step 3).
import android.text.InputType
import android.widget.EditText
import java.util.Locale

/** The list, the app's `src/main/resources/words.txt`, one word a line, read once. */
val WORDS: Set<String> by lazy {
    val list = checkNotNull(WordList::class.java.getResourceAsStream("/words.txt")) {
        "words.txt is not in the app's resources"
    }
    list.bufferedReader(Charsets.US_ASCII).useLines { lines ->
        lines.filter { it.isNotEmpty() }.toSet()
    }
}

private object WordList

/** What may stand between two words: one or more of them, mixed. */
private val SEPARATORS = charArrayOf('.', ' ', '-')

/** What is dropped before the first word and after the last. */
private val ENDS = charArrayOf(' ', '\t', '\r', '\n')

/**
 * The code as the installer typed it, or a scanner read it, read as the middleware reads it.
 * Returns the code as the middleware shows it, five words in lower case joined by dots, or null
 * for anything else. Never send a null: ask the installer to type the code again.
 */
fun deviceCode(typed: String, words: Set<String>): String? {
    // At most 64 characters, each of them ASCII: the middleware counts 64 bytes, and reads no
    // letter outside `a` to `z` as part of a word.
    if (typed.length > 64 || typed.any { it.code > 0x7f }) return null
    val text = typed.trim(*ENDS).lowercase(Locale.ROOT)
    if (text.isEmpty() || text.first() in SEPARATORS || text.last() in SEPARATORS) return null
    val tokens = text.split(*SEPARATORS).filter { it.isNotEmpty() }
    if (tokens.size != 5 || tokens.toSet().size != 5 || !words.containsAll(tokens)) return null
    return tokens.joinToString(".")
}

/** What the letters of the word being typed begin, on the list. */
sealed interface Begun {
    /** One word alone: complete it, and its dot, unless it is the fifth word. */
    data class Word(val word: String) : Begun

    /** More than one: wait for the next letter. By the fourth there is one or none. */
    object Several : Begun

    /** None: show it at once, so the installer retypes the word and spends no attempt. */
    object NoWord : Begun
}

/** What [letters], the letters typed of one word, begin in [words]. */
fun begun(letters: String, words: Set<String>): Begun {
    val typed = letters.lowercase(Locale.ROOT)
    val begins = words.filter { it.startsWith(typed) }
    return when (begins.size) {
        0 -> Begun.NoWord
        1 -> Begun.Word(begins.single())
        else -> Begun.Several
    }
}

/** The code's field: none of the keyboard's own corrections or suggestions. */
fun EditText.forDeviceCode() {
    inputType = InputType.TYPE_CLASS_TEXT or InputType.TYPE_TEXT_VARIATION_VISIBLE_PASSWORD
}

The QR code

Whoever shows the code may show a QR code of it beside the words, for the app to scan. A QR code of a device’s code holds the code as the middleware shows it and nothing else, bronze.farm.loop.prism.tempo, in byte mode at error correction M. A code is at most 34 bytes, five words of six letters and four dots, so every code fits a version 3 symbol, 29 modules a side, which holds 42 bytes at M. The middleware answers the code as text and draws no image: whoever shows the code draws the QR from the PairingCode it was given. A server’s code has no QR.

The app reads the symbol’s text with its camera or the device’s scanner, by the rule a typed code is read by, deviceCode, so the line end a scanner leaves is dropped; shows the five words; and enrols when the installer taps to. It never follows the text as a link, and never reads a host from it: the middleware’s address is the app’s own. A text that is not a code is refused, as a typed one is. A photograph of the QR is a photograph of the words: good for 15 minutes, once, and of no use without the listed serial and, on live, a device that passes attestation.

3. The key, in the Android keystore

The device’s key is P-256, made in the Android keystore under an alias of your choosing, and it never leaves the keystore. It is made with an attestation challenge, so the attestation the keystore writes for it carries that challenge, and the middleware can tell the key was made for this enrolment and no other. Ask for the device’s brand and model in the attestation with setDevicePropertiesAttestationIncluded where the API has it, API 31 and later: the operator’s allowed list admits a device by them.

The challenge is fixed before the key exists. At enrolment it is the SHA-256 of mw-enrol-v1, the code as the middleware shows it, its five words in lower case joined by dots as deviceCode returns them (step 2), and the device’s serial as step 5 reads it, so read the serial before you make the key. At renewal it is the Challenge the middleware answers (step 10).

import android.os.Build
import android.security.keystore.KeyGenParameterSpec
import android.security.keystore.KeyProperties
import java.security.KeyPairGenerator
import java.security.KeyStore
import java.security.ProviderException
import java.security.spec.ECGenParameterSpec

/**
 * Makes a P-256 key in the Android keystore under [alias], attested with [challenge], with the
 * device's brand and model in the attestation where the platform can put them there. Returns
 * whether it did.
 */
fun makeKey(alias: String, challenge: ByteArray): Boolean {
    fun spec(deviceProperties: Boolean): KeyGenParameterSpec {
        val builder = KeyGenParameterSpec.Builder(alias, KeyProperties.PURPOSE_SIGN)
            .setAlgorithmParameterSpec(ECGenParameterSpec("secp256r1"))
            .setDigests(
                KeyProperties.DIGEST_NONE,
                KeyProperties.DIGEST_SHA256,
                KeyProperties.DIGEST_SHA384,
                KeyProperties.DIGEST_SHA512,
            )
            .setAttestationChallenge(challenge)
        if (deviceProperties && Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
            builder.setDevicePropertiesAttestationIncluded(true)
        }
        return builder.build()
    }
    val generator = KeyPairGenerator.getInstance(KeyProperties.KEY_ALGORITHM_EC, "AndroidKeyStore")
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
        try {
            generator.initialize(spec(deviceProperties = true))
            generator.generateKeyPair()
            return true
        } catch (unsupported: ProviderException) {
            // This device cannot attest its brand and model: made again without them.
        }
    }
    generator.initialize(spec(deviceProperties = false))
    generator.generateKeyPair()
    return false
}

/** What `KeyStore.getCertificateChain` gives for [alias], leaf first, as one PEM text. */
fun attestationChainOf(alias: String): String {
    val keyStore = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
    val chain = checkNotNull(keyStore.getCertificateChain(alias)) { "no key under $alias" }
    return chain.joinToString("") { pem("CERTIFICATE", it.encoded) }
}

KeyStore.getCertificateChain gives the attestation: the key’s own certificate first, then the certificates the keystore’s attestation key chains through, to Google’s root. Send all of it, as it comes, in AttestationChain. Do not check it on the device: the middleware checks it, on the server, as Google’s guidance says. The key allows signing with no digest of its own, DIGEST_NONE, beside SHA-256 to SHA-512, for the handshake of step 8: Google’s reference for setDigests, read on 10-Nov-2026, says a key used for TLS client authentication usually needs it, “because TLS/SSL stacks typically generate the necessary digest(s) themselves”.

Where setDevicePropertiesAttestationIncluded is not supported, key generation throws ProviderException, and makeKey makes the key without them. Such a key’s attestation names no brand and no model, so only an allowed-list row naming the firmware’s VerifiedBootKey alone can admit the device: tell the operator which of your devices this is.

Which devices the middleware admits

On live every enrolment and renewal of a device is attested, and the middleware refuses a chain unless: it chains to one of Google’s two attestation roots, and no certificate in it is revoked or suspended; the key is the CSR’s, P-256, made in the keystore’s trusted environment or StrongBox, for signing; the challenge is this call’s; the bootloader is locked and the boot verified; the app is the one registered (step 1); and the device is on the operator’s allowed list, by its attested brand and model, its firmware’s boot key, or both. The allowed list starts empty, so ask the operator to allow your models before the first live enrolment. A middleware set to mark is the one exception, below.

  • BENCH-1, not yet proven on a device. That SUNMI’s models chain to Google’s attestation root. A device certified for Google’s apps should. A device that is not may use its maker’s own root, which the middleware does not take, and such a model is refused at enrolment until the operator decides what a device of it may do. On the unit of the runs above, the chain ended at Android’s software attestation root, which a live middleware refuses.
  • BENCH-3, not yet proven on a device. That the attestation holds attestationIdModel on API 31 and later, and that verifiedBootKey names SUNMI’s firmware signer on older releases. The allowed list cannot tell a model with neither from any other, and treats it as a model with no attestation. On the unit of the runs above, on API 30, the attestation named no model, and its root of trust was the software keymaster’s: a boot key of 32 zero bytes, Unverified and unlocked, which AOSP’s software keymaster on Android 11 attests whatever the boot properties say, though the device’s own properties read verified boot green and a locked bootloader. A live middleware refuses a root of trust the keystore’s secure hardware did not attest.
  • BENCH-6, not yet proven on a device. That a real attestation chain parses as the middleware parses one, on each firmware. The software chain of the unit of the runs above did; no device run has yet tried a chain from secure hardware, a trusted environment or StrongBox.

FUNDiMO’s staging middleware alone can be set to mark a device whose attestation fails rather than refuse it, so that everything but the attestation can be tried on a device that cannot pass it. Set so, at enrolment and at renewal, it admits a device whose chain fails only the checks that are the device’s and its maker’s: a chain not ending at one of Google’s roots or not one the middleware can follow, a certificate in it out of its dates or on Google’s status list, a key not in the trusted environment or StrongBox, a bootloader not locked or a boot not verified, and a device the allowed list does not hold. It also admits one whose app is registered as a debug build alone, and one that sends no chain. It issues the certificate and records on it which checks failed, which the device’s listings show, and the device then works as any other. It refuses as written above everything else: a chain that does not parse, an attestation extension not on the key’s own certificate alone, a key not the CSR’s, a challenge not the call’s, a serial attested in secure hardware that is not the listed one, and an app its vendor has not registered. A SUNMI terminal as FUNDiMO’s bench measured one, its attestation at software level under AOSP’s software attestation root, not Google’s, every tag in softwareEnforced, a boot key of 32 zero bytes and its boot Unverified, is admitted there, marked as failing the root, the hardware, the boot and the model. Production refuses as written, and the sandbox requires no attestation, so it marks nothing. Build the app for the rules above: a device staging marks, a middleware that does not mark refuses.

4. The CSR

The middleware reads one thing from the CSR: its public key. It checks the CSR’s own signature and that the key is P-256, and writes every name in the certificate itself, so the subject says nothing, and holds nothing about the device. The CSR is signed by the keystore key, through a Bouncy Castle ContentSigner that hands the bytes to the keystore, so the key never leaves it.

import java.io.ByteArrayOutputStream
import java.io.OutputStream
import java.security.KeyStore
import java.security.PrivateKey
import java.security.Signature
import org.bouncycastle.asn1.x500.X500Name
import org.bouncycastle.asn1.x509.AlgorithmIdentifier
import org.bouncycastle.asn1.x9.X9ObjectIdentifiers
import org.bouncycastle.operator.ContentSigner
import org.bouncycastle.pkcs.jcajce.JcaPKCS10CertificationRequestBuilder

/** Signs with a keystore key, which signs inside the keystore. */
class KeystoreSigner(key: PrivateKey) : ContentSigner {
    private val signature = Signature.getInstance("SHA256withECDSA").apply { initSign(key) }
    private val written = ByteArrayOutputStream()

    override fun getAlgorithmIdentifier() = AlgorithmIdentifier(X9ObjectIdentifiers.ecdsa_with_SHA256)

    override fun getOutputStream(): OutputStream = written

    override fun getSignature(): ByteArray {
        signature.update(written.toByteArray())
        return signature.sign()
    }
}

/** A CSR for the key under [alias], PEM. The middleware reads its key alone. */
fun csrFor(alias: String): String {
    val keyStore = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
    val key = keyStore.getKey(alias, null) as PrivateKey
    val publicKey = keyStore.getCertificate(alias).publicKey
    val csr = JcaPKCS10CertificationRequestBuilder(X500Name("CN=device"), publicKey)
        .build(KeystoreSigner(key))
    return pem("CERTIFICATE REQUEST", csr.encoded)
}

A CSR whose signature does not verify, or whose key is not P-256, is refused 400 invalid_field, with Fields naming CertificateSigningRequest.

import java.util.UUID

import okhttp3.RequestBody.Companion.toRequestBody
import org.json.JSONObject

/**
 * An enrolment built and not yet answered: the keystore alias of its key, and its request. Keep
 * it while the code's screen is open, and send this same one again after no answer, a `429` or
 * a `5xx`: it may have spent the code, and a spent code refuses any key but the one it was
 * spent with, which inside the code's 15 minutes it answers `200`.
 */
class Enrolment(val alias: String, val request: Request)

/**
 * Builds the enrolment of this device with the code the installer typed and its serial: a new
 * keystore key under a new alias, its CSR and its attestation. Build a new one for a new code,
 * or after a `400` or a `403` of the table below, a verdict on this very enrolment. Never after
 * no answer, a `429` or a `5xx`, which may follow an enrolment that spent the code.
 */
fun enrolment(typedCode: String, serial: String): Enrolment {
    val code = requireNotNull(deviceCode(typedCode, WORDS)) { "not five words of the list: type it again" }
    require(SERIAL.matches(serial)) { "not a serial a listing holds" }
    val alias = "mw-" + UUID.randomUUID()
    makeKey(alias, enrolmentChallenge(code, serial))
    val body = JSONObject()
        .put("PairingCode", code)
        .put("CertificateSigningRequest", csrFor(alias))
        .put("SerialNumber", serial)
        .put("AttestationChain", attestationChainOf(alias))
        .toString()
        .toRequestBody(JSON)
    // No certificate yet: the code is the credential.
    return Enrolment(alias, Request.Builder().url("$MW/v1/enrol").post(body).build())
}

/**
 * Sends [enrolment] until an answer comes. Throws `IOException` where none came, and
 * `JSONException` where a `2xx`'s body was not JSON: send the same [enrolment] again on the
 * person's next tap, never a new one.
 */
fun enrolDevice(enrolment: Enrolment): Answer = sendUntilAnswered(plain, enrolment.request)

The answer is 201:

{ "CertificateChain": "-----BEGIN CERTIFICATE-----\n...", "POIIdentification": "poi_...", "SpiffeId": "spiffe://.../live/terminal/poi_...", "NotAfter": "...", "RenewFrom": "..." }

SpiffeId is the certificate’s URI. Its host is the trust domain of the deployment that issued it, which need not be the address you call, and its first segment is the environment, live or sandbox. A register’s answer names RegisterIdentification where a terminal’s names POIIdentification. NotAfter is when the certificate ends, 30 days on, and RenewFrom is day 15. If an answer is lost, send the same body again inside the code’s 15 minutes, as sendUntilAnswered does: the same code and the same key answer 200 with the certificate already issued. The same code with another key is 403 code_not_valid, so never make a new key to repeat a call that got no answer: keep the Enrolment until it is answered, and send it again.

When enrolment is refused

Changed in v0.3.0.

Each refusal from the middleware has the body { "Error": { "Code": "...", "Message": "...", "Fields": [] } }. The edge’s 429 is the one that differs: the edge in front of a hosted middleware sends it, and its body is the edge’s own. 7. Store the chain against the alias

Changed in v0.5.0.

The 201’s CertificateChain is two certificates, PEM: the device’s own, then the issuing certificate. The device presents both at the handshake of every call from now on (step 8). A certificate is public, so the chain needs no protecting, but it belongs to the key under one alias, and is kept against that alias. The app keeps the alias of the key it connects with, current; while a new certificate waits for its first use, that one’s, next; and while a renewal it sent waits for a verdict, that renewal’s alias and body, renewal (step 10).

import android.content.Context
import java.io.File
import java.io.IOException
import java.security.cert.CertificateFactory
import java.security.cert.X509Certificate

/** The chains the middleware issued, each against the keystore alias of its key, and which is in use. */
class Identities(context: Context) {
    private val prefs = context.getSharedPreferences("mw-identity", Context.MODE_PRIVATE)
    private val dir = File(context.noBackupFilesDir, "mw").apply { mkdirs() }

    /** The alias of the key the device connects with. */
    var current: String?
        get() = prefs.getString("current", null)
        set(alias) {
            prefs.edit().putString("current", alias).commit()
        }

    /** The alias of a certificate issued and not yet used: a renewal's or a re-enrolment's. */
    var next: String?
        get() = prefs.getString("next", null)
        set(alias) {
            prefs.edit().putString("next", alias).commit()
        }

    /**
     * A renewal sent and not yet settled: the alias of its new key and its body, kept until a
     * `201` or a `200` of it is kept, or a refusal says no certificate is over its key (step 10).
     */
    var renewal: Pair<String, String>?
        get() {
            val alias = prefs.getString("renewal-alias", null) ?: return null
            val body = prefs.getString("renewal-body", null) ?: return null
            return alias to body
        }
        set(sent) {
            prefs.edit()
                .putString("renewal-alias", sent?.first)
                .putString("renewal-body", sent?.second)
                .commit()
        }

    /** Keeps a `201`'s `CertificateChain` against [alias], whole or not at all. */
    fun storeChain(alias: String, certificateChain: String) {
        val partial = File(dir, "$alias.pem.partial")
        partial.writeText(certificateChain)
        if (!partial.renameTo(File(dir, "$alias.pem"))) {
            throw IOException("cannot keep the chain of $alias")
        }
    }

    /** The chain kept against [alias], leaf first, or null. */
    fun chain(alias: String): Array<X509Certificate>? {
        val file = File(dir, "$alias.pem")
        if (!file.exists()) return null
        return file.inputStream().use { stream ->
            CertificateFactory.getInstance("X.509")
                .generateCertificates(stream)
                .map { it as X509Certificate }
                .toTypedArray()
        }
    }

    /** Forgets the chain of a key that was deleted. */
    fun forget(alias: String) {
        File(dir, "$alias.pem").delete()
    }
}

/** After the first enrolment: the chain kept against the new alias, which is now current. */
fun enrolled(identities: Identities, enrolment: Enrolment): Answer {
    val answer = enrolDevice(enrolment)
    if (answer is Answer.Ok) {
        identities.storeChain(enrolment.alias, answer.body.getString("CertificateChain"))
        identities.current = enrolment.alias
    }
    // A refusal: the table of step 6 says what to tell the installer.
    return answer
}

A 201 ends any wait a refusal set: connect at once on the new certificate. A new code re-pairs the device, so the credential it held, a certificate or in the sandbox its key, is refused 403 not_permitted, which the holder’s table backs off an hour. That hour is for the credential refused, and the middleware takes the new certificate at once.

The chain is kept in the app’s no-backup storage, because a backup restored to another device would hold a chain whose key is not there. A certificate’s key is kept nowhere but the keystore.

8. Give OkHttp the key: an X509ExtendedKeyManager

Every call after enrolment presents the certificate at the TLS handshake. The key stays in the keystore, so OkHttp is given a key manager that names the keystore alias, hands over the kept chain, and gives the TLS stack the keystore’s handle to the key, which signs inside the keystore. One OkHttp client built on it serves REST and the WebSocket alike: a register’s sales and links, a terminal’s connection (docs/api/terminal.md, Connect), the daily check and renewal.

import java.net.Socket
import java.security.KeyStore
import java.security.Principal
import java.security.PrivateKey
import java.security.cert.X509Certificate
import java.util.concurrent.TimeUnit
import javax.net.ssl.SSLContext
import javax.net.ssl.SSLEngine
import javax.net.ssl.TrustManagerFactory
import javax.net.ssl.X509ExtendedKeyManager
import javax.net.ssl.X509TrustManager
import okhttp3.OkHttpClient
import okhttp3.Request
import okhttp3.WebSocket
import okhttp3.WebSocketListener

/** Presents the keystore key under [alias], with the chain the middleware issued for it, and no other. */
class KeystoreKeyManager(
    private val alias: String,
    private val chain: Array<X509Certificate>,
) : X509ExtendedKeyManager() {
    private val keyStore = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }

    override fun chooseClientAlias(
        keyType: Array<out String>?,
        issuers: Array<out Principal>?,
        socket: Socket?,
    ): String = alias

    override fun chooseEngineClientAlias(
        keyType: Array<out String>?,
        issuers: Array<out Principal>?,
        engine: SSLEngine?,
    ): String = alias

    override fun getClientAliases(keyType: String?, issuers: Array<out Principal>?): Array<String> =
        arrayOf(alias)

    override fun getCertificateChain(alias: String?): Array<X509Certificate>? =
        if (alias == this.alias) chain else null

    override fun getPrivateKey(alias: String?): PrivateKey? =
        if (alias == this.alias) keyStore.getKey(this.alias, null) as? PrivateKey else null

    override fun chooseServerAlias(
        keyType: String?,
        issuers: Array<out Principal>?,
        socket: Socket?,
    ): String? = null

    override fun getServerAliases(keyType: String?, issuers: Array<out Principal>?): Array<String>? =
        null
}

/** A client presenting the key under [alias], for REST and the WebSocket alike. */
fun clientFor(alias: String, chain: Array<X509Certificate>): OkHttpClient {
    val trustFactory = TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm())
    trustFactory.init(null as KeyStore?)
    val trust = trustFactory.trustManagers.filterIsInstance<X509TrustManager>().first()
    val tls = SSLContext.getInstance("TLS")
    tls.init(arrayOf(KeystoreKeyManager(alias, chain)), arrayOf(trust), null)
    return OkHttpClient.Builder()
        .sslSocketFactory(tls.socketFactory, trust)
        // OkHttp answers the middleware's Pings itself and never shows them: send its own.
        .pingInterval(30, TimeUnit.SECONDS)
        .build()
}

/**
 * A terminal's connection, `docs/api/terminal.md`, Connect, on [client]. OkHttp opens a
 * WebSocket from an https address, and presents the key at its handshake as for REST.
 */
fun connect(client: OkHttpClient, poiIdentification: String, listener: WebSocketListener): WebSocket {
    val request = Request.Builder().url("$MW/v1/terminals/$poiIdentification/connect").build()
    return client.newWebSocket(request, listener)
}

Build the client once for each alias, and use it for every call while that alias is in use. Never change which key one client presents: a client’s TLS context keeps its sessions, and a resumed session stands on the certificate of the handshake it resumes, so a new certificate goes with a new client (step 10). Send no Authorization header on a client that presents a certificate: the two together are refused 401 certificate_invalid. The client’s pingInterval is what keeps the terminal’s WebSocket to the contract’s Hold (docs/api/terminal.md, Hold), since OkHttp shows the app none of the middleware’s Pings.

9. The daily check: GET /v1/certificates/self

Changed in v0.5.0.

Once a day the device sends GET /v1/certificates/self, on its own certificate. The middleware answers when the certificate ends, and whether to renew:

{ "NotAfter": "...", "RenewFrom": "...", "RenewNow": true }

Renew when RenewNow is true, and not before, and never while a next certificate waits for its first use (step 10). The middleware decides, so the device’s clock does not matter. RenewNow reads true only on the newest certificate in use, from RenewFrom on, and false on a certificate that is retired.

import android.content.Context
import androidx.work.ExistingPeriodicWorkPolicy
import androidx.work.PeriodicWorkRequestBuilder
import androidx.work.WorkManager
import androidx.work.Worker
import androidx.work.WorkerParameters
import java.io.IOException
import java.util.concurrent.TimeUnit
import okhttp3.Request

/** Once a day: a certificate waiting for its first use, then the daily check, then any renewal. */
class DailyCheck(context: Context, params: WorkerParameters) : Worker(context, params) {
    override fun doWork(): Result = try {
        val identities = Identities(applicationContext)
        firstUse(identities)
        val alias = identities.current
        val chain = alias?.let { identities.chain(it) }
        if (alias != null && chain != null) {
            val client = clientFor(alias, chain)
            val self = Request.Builder().url("$MW/v1/certificates/self").build()
            val answer = call(client, self)
            // Never while a next waits: a second renewal would retire it (step 10).
            if (answer is Answer.Ok && answer.body.getBoolean("RenewNow") && identities.next == null) {
                if (renew(client, identities) is Answer.Ok) firstUse(identities)
            }
            // A refusal: the holder's table, below.
        }
        Result.success()
    } catch (noAnswer: IOException) {
        Result.retry()
    }
}

/** One daily check, however often this is called. */
fun scheduleDailyCheck(context: Context) {
    WorkManager.getInstance(context).enqueueUniquePeriodicWork(
        "mw-daily-check",
        ExistingPeriodicWorkPolicy.KEEP,
        PeriodicWorkRequestBuilder<DailyCheck>(1, TimeUnit.DAYS).build(),
    )
}

A refusal of the daily check is read by the holder’s table (What a holder of a dead certificate does, below). A call that gets no answer is tried again later.

10. Renew: a new key under a new alias

Changed in v0.5.0.

A certificate renews from day 15, always with a new key. So a device proves its state again every 15 days, and a device rooted after it enrolled loses its identity within one lifetime of a certificate, but on a middleware set to mark (step 3), which marks it instead. In the sandbox, a certificate enrolled on a code asked with "Due": true is due at once (In the sandbox, above).

  1. Send POST /v1/certificates/challenge on the current certificate, with no body and with Content-Length: 0: over HTTP/1.1, the edge in front of a hosted middleware refuses it without that header, with a 411 of its own. The 201 holds Challenge, 32 bytes as 64 hex characters, and ExpiresInSeconds, 600.
  2. Make a new key under a new alias with those 32 bytes as its attestation challenge (step 3), and a CSR for it (step 4).
  3. Send POST /v1/certificates/renew with CertificateSigningRequest and AttestationChain, on the current certificate, inside the challenge’s 10 minutes, and keep the body and the new key’s alias until a verdict on them. The 201 is enrolment’s. If an answer is lost, or a 2xx comes that the device cannot read or keep, send the same body again, at the next daily check if not before, and ask no new challenge meanwhile: a CSR of the key the middleware issued for last answers 200 with that certificate, whatever became of its challenge, and a second renewal would retire it.
  4. Keep the new chain against the new alias, as the next certificate (step 7), and use it from the next connection, on a new client of its own (step 8).
  5. Once a call on the new certificate has been answered, it is current. Only then delete the old key.
import java.security.KeyStore
import java.util.UUID
import okhttp3.OkHttpClient
import okhttp3.Request
import okhttp3.RequestBody.Companion.toRequestBody
import org.json.JSONObject

/**
 * Renews on [client], the current certificate's. A renewal sent and not yet settled is sent again
 * as it was, with no new challenge: a certificate may have been issued over its key, and its own
 * body is answered `200` with that one. Otherwise a challenge, a new key under a new alias made
 * with it, and the renewal, kept before it is sent. A certificate issued is kept as the next one.
 */
fun renew(client: OkHttpClient, identities: Identities): Answer {
    val (alias, body) = identities.renewal ?: run {
        val ask = Request.Builder()
            .url("$MW/v1/certificates/challenge")
            .post(ByteArray(0).toRequestBody())
            .build()
        val issued = call(client, ask)
        if (issued !is Answer.Ok) return issued
        val challenge = requireNotNull(bytesOfHex(issued.body.getString("Challenge"))) {
            "a challenge is 64 hex characters"
        }
        val alias = "mw-" + UUID.randomUUID()
        makeKey(alias, challenge)
        val body = JSONObject()
            .put("CertificateSigningRequest", csrFor(alias))
            .put("AttestationChain", attestationChainOf(alias))
            .toString()
        (alias to body).also { identities.renewal = it }
    }
    val request = Request.Builder()
        .url("$MW/v1/certificates/renew")
        .post(body.toRequestBody(JSON))
        .build()
    val renewed = sendUntilAnswered(client, request)
    if (renewed is Answer.Ok) {
        identities.storeChain(alias, renewed.body.getString("CertificateChain"))
        identities.next = alias
        identities.renewal = null
    } else if (renewed is Answer.Refused && renewed.code in NONE_ISSUED) {
        // No certificate not yet used is over the key: delete it, unless it is one it keeps.
        if (alias != identities.current && alias != identities.next) {
            KeyStore.getInstance("AndroidKeyStore").apply { load(null) }.deleteEntry(alias)
        }
        identities.renewal = null
    }
    // Any other answer is no verdict on the key: the next daily check sends the same body.
    return renewed
}

/** A renewal's refusals that say no certificate not yet used is over the key it sent. */
val NONE_ISSUED = setOf(
    "invalid_json", "unknown_field", "missing_field", "invalid_field", "renewal_not_due",
    "challenge_not_valid", "attestation_failed", "app_identity_unknown", "model_not_allowed",
    "renewal_rate",
)

/**
 * The first use of the next certificate, on a client of its own. Once the middleware has answered on
 * it, it is current, and only then are the old key, and any key a refused renewal or a re-pair left,
 * deleted. An app holds one identity, of the one environment it chose before its first enrolment
 * (`/docs/api/environments.md`), so every other `mw-` alias is one of these. Returns whether it moved.
 */
fun firstUse(identities: Identities): Boolean {
    val next = identities.next ?: return false
    val chain = identities.chain(next) ?: return false
    val self = Request.Builder().url("$MW/v1/certificates/self").build()
    if (call(clientFor(next, chain), self) !is Answer.Ok) return false
    identities.current = next
    identities.next = null
    val keyStore = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
    for (alias in keyStore.aliases().toList()) {
        if (alias.startsWith("mw-") && alias != next) {
            keyStore.deleteEntry(alias)
            identities.forget(alias)
        }
    }
    identities.renewal = null
    return true
}

The old certificate stays good until the new one is first used, and for an hour after, MW_CERT_OVERLAP_SECS. Move every connection to the new client inside that hour: a terminal moves its WebSocket between sales. Past the hour, a call on the old certificate is refused 403 certificate_retired, and a terminal’s WebSocket still open on it is closed. If the first call on the new certificate gets no answer, go on with the old one, which is good until then, and try the new one again later.

Run the daily check, a renewal and a first use one at a time. A second renewal retires a certificate the first issued that is not yet used, and the middleware warns the operator of it, as the sign of an identity copied. So renew only while no next certificate waits for its first use, and send a renewal that waits for a verdict again as it was, never a new one in its place.

A device never deletes its key or its certificate on a refusal, any of those above. Its key is that of a certificate it keeps, the current or the next. A device can recover from a mistake of the middleware’s by a fix on the middleware’s side, and a key deleted cannot be recovered. A device holding a certificate makes a new key only to renew, or when a person brings a new code, and deletes an old key only once a call on the certificate that follows it has been answered. A device decides none of this by its own clock.

A key made for a renewal, which no certificate the device keeps is over, is kept with the renewal’s body until a 201 or a 200 of it is kept, or the renewal is refused 400 invalid_json, unknown_field, missing_field or invalid_field, 409 renewal_not_due, 403 challenge_not_valid, attestation_failed, app_identity_unknown or model_not_allowed, or 429 renewal_rate. An enrolment’s key is kept until a 201 or a 200 of it is kept, or a new code is typed: past its code’s 15 minutes no answer can bring its certificate, and the new code retires any the old one issued (step 11).

11. Re-enrol with a new code

A device off longer than its certificate, past its NotAfter, re-enrols with a new code. So does a device told after three hourly tries that it needs one, and a device its listing party re-paired, which is refused 403 not_permitted until a person brings it the new code. This is the one case after the first enrolment in which a person is needed.

  1. The installer asks the listing party for a new code: POST /v1/terminals/{POIIdentification}/pairing-code for a terminal, POST /v1/registers/{RegisterIdentification}/pairing-code for a register, or in the sandbox POST /sandbox/v1/codes. A new code re-pairs the device, which retires its certificates.
  2. The installer opens the app’s enrolment screen from its menu or settings, on the device as it is, and types the new code’s words, or scans its QR code (step 2, and The enrolment screen).
  3. The app enrols as it did the first time (step 6), with a new key under a new alias, and the challenge of the new code.
  4. It keeps the chain as the next certificate, and deletes the old key once a call on the new one has been answered, as a renewal does (step 10).
  5. A 201 ends any wait a refusal set: it connects at once on the new certificate, though the old one’s 403 not_permitted set an hour (step 7).
import java.io.IOException

/**
 * Re-enrolment with the new code the installer typed, built by `enrolment`. The new certificate
 * is kept as the next one, and the old key stays until a call on it has been answered. A first
 * use that gets no answer leaves it next: the screen says the device is enrolled and not yet
 * connected, and tries `firstUse` again, which needs no code, and never the enrolment, which
 * the code refuses once its 15 minutes end.
 */
fun reEnrol(identities: Identities, enrolment: Enrolment): Answer {
    val answer = enrolDevice(enrolment)
    if (answer is Answer.Ok) {
        identities.storeChain(enrolment.alias, answer.body.getString("CertificateChain"))
        identities.next = enrolment.alias
        try {
            firstUse(identities)
        } catch (noAnswer: IOException) {
            // Still next: the screen tries the first use again (SCREEN-24).
        }
    }
    // A refusal: the table of step 6.
    return answer
}

The device keeps its id, POIIdentification or RegisterIdentification, and a register’s links to terminals stand: a re-pair ends none.
